# 发布自动化与双端产物计划

> 本计划只描述方案与验收边界，不包含 workflow 实现代码。
> 当前状态：Windows 构建 CI 与 release workflow 已实现，尚未在 GitHub Actions 实际运行，也未创建发布 tag。

## 1. 目标

在 GitHub 上按版本发布双端安装包：

- macOS：DMG
- Windows：NSIS 安装包
- 同一版本使用同一 tag、同一提交与同一 `Cargo.lock`
- 发布前自动验证版本一致性、构建产物与校验和
- 默认创建 **draft release**，真机验收通过后由人工发布

## 2. 非目标

- 不做自动更新（Tauri updater）。
- 不做 Apple 公证或 Windows 代码签名；后续单独做。
- 不自动发布 stable；draft 必须人工确认。
- 不把源码构建成功当作真机验收。
- 不发布未通过 macOS/Windows 真机验收的正式版本。

## 3. 当前基础

| 项目 | 现状 |
|---|---|
| 版本源 | 根 `Cargo.toml` 与 `apps/mixer-gui/tauri.conf.json`，当前 `0.1.0` |
| macOS 构建 | `apps/mixer-gui/build-app.sh`，生成 DMG |
| Windows 构建 | `apps/mixer-gui/build-app-windows.ps1`，生成 NSIS |
| 默认变声后端 | C++/Signalsmith，需要 LLVM/libclang |
| Node 依赖 | `package-lock.json` 已入库，CI 可用 `npm ci` |
| 现有 CI | `quality.yml` 已安装 LLVM、跑测试；没有 release workflow |
| Windows 真机 | 用户报告已验，逐项证据待在 `变声器真机验收-Windows.md` 补齐 |
| macOS 真机 | 仍为 D，需补环回、听感与 V-18 |

## 4. 版本与 tag 规则

- tag 使用 `vMAJOR.MINOR.PATCH`，例如 `v0.1.0`。
- tag 必须指向 `master` 上的发布提交。
- 发布前必须同时更新：
  - 根 `Cargo.toml` 的 workspace `version`
  - `apps/mixer-gui/tauri.conf.json` 的 `version`
  - `Cargo.lock`（重新生成）
  - `CHANGELOG.md`
- 三项版本必须完全一致；不一致时 release workflow 直接失败。
- 已有 tag 不可覆盖；修正版本必须递增 patch。
- 发布提交与 tag 必须来自同一 SHA。

## 5. 自动 workflow 设计

新增 `.github/workflows/release.yml`，触发条件：

```text
on:
  push:
    tags: ["v*"]
  workflow_dispatch:
    inputs:
      tag: 用于不发布产物的手动构建演练
```

### 5.1 preflight

- 在 `ubuntu-latest` 运行。
- 校验：
  - tag 形如 `vX.Y.Z`
  - tag 版本等于 `tauri.conf.json.version`
  - tag 版本等于 workspace `Cargo.toml.version`
  - `Cargo.lock` 已锁定
- 输出规范化 tag、版本、ref 与产品名给后续 job；产物名由版本派生。
- 失败即停止，不构建、不创建 release。

### 5.2 macOS job

- `macos-latest`
- 安装 Node 22、Rust stable（含 aarch64 / x86_64 target）、LLVM；镜像已带 LLVM 时复用。
- `npm ci`
- `MIXER_TARGET=universal-apple-darwin ./apps/mixer-gui/build-app.sh`
- 校验：
  - DMG 存在
  - App 签名有效
  - App 内含 `LICENSE` 与 `THIRD-PARTY-NOTICES.md`
  - 二进制同时含 arm64 与 x86_64
- 生成 DMG 的 SHA-256。
- 上传 artifact：DMG + checksum。

### 5.3 Windows job

- `windows-latest`
- 安装 Node 22、Rust stable、LLVM；镜像已带 LLVM 时复用。
- `npm ci`
- `powershell -ExecutionPolicy Bypass -File apps/mixer-gui/build-app-windows.ps1`
- 校验：
  - NSIS setup.exe 存在
  - `installer.nsi` 含 LICENSE 与 THIRD-PARTY-NOTICES.md
  - 构建目录有分发文档副本
- 生成 setup.exe 的 SHA-256。
- 上传 artifact：setup.exe + checksum。

> Windows 原生 CI 是 C++ 后端的权威编译检查；macOS 上的交叉检查不替代。

### 5.4 release job

- `ubuntu-latest`
- `needs: [preflight, macos, windows]`
- `permissions: contents: write`
- 下载两个 artifact，分别校验各自的 `SHA256SUMS.txt`。
- 合并 `SHA256SUMS.txt`。
- 用 `gh release create "$TAG" --draft --generate-notes` 上传：
  - `mixer-gui_<version>_macos.dmg`
  - `mixer-gui_<version>_windows_x64_setup.exe`
  - `SHA256SUMS.txt`
- 不使用 `--latest`，不自动发布 stable。
- 已有 release 时 `gh release create` 失败，不覆盖资产；人工处理。
- 失败时保留已构建 artifact，便于排查。

## 6. 产物命名

建议使用 ASCII，避免部分下载工具和脚本对中文/空格处理不一致：

```text
mixer-gui_0.1.0_macos.dmg
mixer-gui_0.1.0_windows_x64_setup.exe
SHA256SUMS.txt
```

Release 标题与说明仍用中文产品名。`tauri.conf.json` 的 `productName` 不变，安装后显示中文名。

## 7. 发布流程

1. 更新版本与 `CHANGELOG.md`，提交到 `master`。
2. 跑完整门禁：
   - `cargo fmt --all --check`
   - `cargo clippy --locked --workspace --all-targets -- -D warnings`
   - `cargo test --locked --workspace --all-targets`
   - `cargo test --locked -p audio-core --features voice`
   - `cargo test --locked -p audio-session --features voice`
   - Node 套件
   - `./tools/win-cross-check.sh`
3. `git tag -a vX.Y.Z -m "vX.Y.Z"`，推送 tag。
4. 等 release workflow 完成，检查 draft 资产。
5. 在干净环境安装 macOS/Windows 包，完成真机验收。
6. 人工 Publish draft。
7. 若任一端失败：保留 draft，递增版本修复后重新发 tag；不覆盖已发布资产。

## 8. 验收门槛

- 版本一致性检查通过。
- macOS DMG 可挂载、App 签名有效、含声明与 entitlement。
- Windows NSIS 可安装、安装目录含声明、无缺失 DLL。
- 两端产物来自同一 tag / 同一提交 / 同一 `Cargo.lock`。
- `SHA256SUMS.txt` 可校验。
- macOS 与 Windows 真机功能矩阵、听感与延迟差值达到验收记录要求。
- V-18/V-19 未关闭时，release 保持 draft，不发布 stable。

## 9. 签名与分发边界

- macOS CI 无证书时使用 ad-hoc 签名；用户首次打开需 Control-click。
- Windows 安装包未签名，SmartScreen 会提示。
- 后续若有 Apple Developer ID / Windows 代码签名证书，通过 GitHub Secrets 注入；不在本计划内。
- 发布说明必须写明系统要求、虚拟声卡依赖、未签名提示与已知限制。

## 10. 风险与回滚

| 风险 | 应对 |
|---|---|
| Windows NSIS 在 CI 失败 | 先加 Windows 构建 CI 或 workflow_dispatch 演练，不直接发 tag |
| 版本不一致 | preflight 直接失败 |
| 资产名冲突 | 不覆盖已有 release；递增版本 |
| 构建来自错误提交 | checkout tag SHA，日志打印 SHA |
| 未验收就发布 | 默认 draft，人工 Publish |
| 签名缺失 | 发布说明明确提示；后续补证书 |

## 11. 实施顺序

1. 补齐 Windows 真机验收记录与证据。
2. 先加 Windows 构建 job（可以只在 `workflow_dispatch` 跑），确认 NSIS 产物。
3. 加 `release.yml` 的 preflight 与双端构建。
4. 用测试 tag 触发 draft，检查资产与 checksum。
5. 完成 macOS 真机验收。
6. 发布首个 draft → 人工 Publish。
