# M0 验证方案（Go / No-Go 实验）

> 目标：**在写任何代码之前**，用现成工具回答"这个产品能不能成立"。
> 成本：**半天时间 + 0 元**。产出：一份填好的数据表 + 一个明确的 go / no-go 决定。
> 配套：[技术设计-音频架构与驱动.md](../engineering/技术设计-音频架构与驱动.md)、[产品设计-交互与功能规格.md](../product/产品设计-交互与功能规格.md)

---

## 0. 为什么必须先做这个

方案里有三个假设，**每一个都能单独杀死这个产品，而它们都不能靠推理确认**：

| # | 假设 | 如果错了会怎样 |
|---|---|---|
| **H1** | 队友语音链路的降噪不会把我们的音频吃掉 | 产品核心价值归零 |
| **H2** | 全局热键在目标游戏里可用 | 核心体验归零（用户必须切出游戏） |
| **H3** | VB-CABLE 在 macOS 26 上能正常工作 | 阶段 1 的技术路线作废 |

**半天时间可以验证全部三个。** 跳过这一步直接开发，是在赌。

## 1. 准备清单

| 项 | 说明 |
|---|---|
| 一台 Mac | ✅ 你的机器（macOS 26.6.1） |
| 一台 Windows | 后续验证用 |
| 一个真人队友 | ⚠️ **必需，不能自己听自己**。用 Discord 或游戏内置语音 |
| VB-CABLE (macOS) | https://vb-cable.com —— 免费，捐赠制 |
| 一个能选输出设备的播放器 | 系统自带的"音乐"App 或任意播放器 |
| 测试音频素材 | 见 §2 |
| 秒表 / 手机录音 | 记录主观听感 |

### 测试音频素材（提前准备 5 个文件）

用任意音频编辑工具（Audacity / 系统自带的 QuickTime 剪辑）生成 **5 个内容相同、电平不同的文件**，每个 10 秒：

| 文件名 | 内容 | RMS 电平 |
|---|---|---|
| `tone_-30dBFS.wav` | 一段音乐（建议选有鼓点+人声的流行乐） | −30 dBFS |
| `tone_-24dBFS.wav` | 同上 | −24 dBFS |
| `tone_-18dBFS.wav` | 同上 | −18 dBFS |
| `tone_-12dBFS.wav` | 同上 | −12 dBFS |
| `tone_-6dBFS.wav` | 同上 | −6 dBFS |

> 这 5 个文件是**实验 2 的核心工具**——它们能直接测出"降噪在哪个电平开始吃音频"。

## 2. 实验 1：端到端链路打通（H3）

**目的**：验证 macOS 26 上"播放 → 虚拟麦克风 → 队友听到"这条链路本身能通。

| 步骤 | 操作 |
|---|---|
| 1 | 安装 VB-CABLE (macOS)，按提示完成，**不需要重启电脑** |
| 2 | 打开"音频 MIDI 设置"（Audio MIDI Setup），确认出现 `VB-Cable` 设备 |
| 3 | 打开系统设置 → 声音，确认输入/输出列表里能看到它 |
| 4 | 打开播放器，**输出设备选 `VB-Cable`** |
| 5 | 打开 Discord（或游戏），**输入设备选 `VB-Cable`** |
| 6 | 播放测试音频 |
| 7 | **问队友：听到了吗？** |

### 记录

| 项 | 结果 |
|---|---|
| VB-CABLE 在 macOS 26.6.1 上是否正常安装 | ☐ 是 ☐ 否，现象：______ |
| 播放器输出列表是否出现 VB-Cable | ☐ 是 ☐ 否 |
| Discord 输入列表是否出现 VB-Cable | ☐ 是 ☐ 否 |
| **队友是否听到** | ☐ 清楚 ☐ 模糊 ☐ 听不到 |
| 切换设备后是否需要重启 Discord/游戏 | ☐ 需要 ☐ 不需要 |
| 从播放到队友听到的**主观延迟** | ______ 秒（用秒表粗测） |
| 是否有爆音 / 卡顿 / 杂音 | ☐ 无 ☐ 有，现象：______ |

> ⚠️ **不要自己听自己**。用队友的耳朵判断，这是唯一有效的验证。

## 3. 实验 2：降噪阈值测试（H1）★ 最关键

**目的**：测出"队友的语音软件在什么电平开始把我们的音频当噪音删掉"。

这是整个产品**能不能成立**的实验。

### 步骤

| 步骤 | 操作 |
|---|---|
| 1 | 保持实验 1 的链路 |
| 2 | 让队友打开他的语音软件设置（Discord：设置 → 语音和视频） |
| 3 | **第一轮：队友开启噪声抑制（Krisp）+ 回声消除** |
| 4 | 依次播放 5 个文件（从 −30 到 −6） |
| 5 | 每播一个，问队友："听到了吗？清楚吗？" |
| 6 | **第二轮：队友关闭噪声抑制 + 回声消除** |
| 7 | 重复播放 5 个文件 |

### 记录表（让队友逐项打分）

| 播放电平 | 降噪**开** · 能否听到 | 降噪**开** · 音质（1-5） | 降噪**关** · 能否听到 | 降噪**关** · 音质（1-5） |
|---|---|---|---|---|
| −30 dBFS | | | | |
| −24 dBFS | | | | |
| −18 dBFS | | | | |
| −12 dBFS | | | | |
| −6 dBFS | | | | |

**补充信息**：
- 队友用的语音软件：☐ Discord ☐ 游戏内置 ☐ 其他：______
- 是否有"自动增益控制"选项：☐ 有，状态：______ ☐ 无

### 判定规则

| 结果 | 含义 | 行动 |
|---|---|---|
| 降噪**关**时全部能听清 | ✅ 产品成立 | 继续，**但必须把"关闭降噪"做成引导流程** |
| 降噪**开**时 −12 dBFS 以上能听清 | ✅ 产品成立 | 电平校准的目标值定在 −15 ～ −12 dBFS |
| 降噪**开**时全部听不到 | ⚠️ 需要设计绕行方案 | 见下方"如果 H1 失败" |
| 降噪**关**时也听不清 | 🔴 链路有问题 | 回到实验 1 排查 |

## 4. 实验 3：人声 + 音效同时送（架构验证）

**目的**：验证"真实麦克风 + 音效同时混入虚拟麦克风"在真实语音链路上可行，且**你的说话声不会被音效压掉**。

实验 1、2 只验证了"纯音效"。但我们的产品是**混音**，这是两回事。

### 方法（不写代码）

用 **VoiceMeeter**（免费）或 macOS 上的 **Loopback 试用版**做一次手动混音：

```
真实麦克风 ──┐
             ├──► 混音 ──► VB-Cable ──► Discord ──► 队友
播放器  ────┘
```

若不想装额外软件，最低成本的近似验证：

| 步骤 | 操作 |
|---|---|
| 1 | 播放器输出 → `VB-Cable`（音效进链路） |
| 2 | 同时**对着麦克风说话** |
| 3 | 问队友：能不能**同时**听到音乐和你的声音？ |

> 注意：这个简化版里你的说话声走的是**真实麦克风 → 某条通路**，不一定能进 VB-Cable。所以**建议还是装 VoiceMeeter** 做一次正确验证——它是免费的，且能确认"混音"这条路走得通。

### 记录

| 项 | 结果 |
|---|---|
| 队友能同时听到人声和音效 | ☐ 是 ☐ 否 |
| 音效是否把你的说话声压低（AGC 抽吸感） | ☐ 无 ☐ 轻微 ☐ 明显 |
| 音效音量调到多少时人声仍清晰 | ______ |

## 5. 实验 4：全局热键在游戏里可用（H2）★ 高风险项

**目的**：验证用户**不切出游戏**就能触发播放。

> 这是被严重低估的风险。很多游戏在全屏独占 / 反作弊环境下会吞掉全局热键。**如果热键在主力游戏里失效，"游戏优先"这个核心原则就不成立。**

### 方法

先不写 App，用现成工具代替：

| 方案 | 怎么做 |
|---|---|
| **方案 A（推荐）** | 用 Soundpad 的免费 Demo（如果有）或任意支持全局热键的音效板工具 |
| **方案 B** | 用 macOS 的"快捷指令"绑定一个全局快捷键，触发播放音频 |
| **方案 C** | 用 AutoHotkey（Windows）/ Karabiner（macOS）注册全局热键，触发播放脚本 |

然后：

| 步骤 | 操作 |
|---|---|
| 1 | 启动目标游戏（**全屏模式**，不是窗口化） |
| 2 | 按热键 |
| 3 | 观察是否触发（听队友反馈 / 看游戏是否有反应） |

### 记录表

| 游戏 | 显示模式 | 热键是否可用 | 备注 |
|---|---|---|---|
| ______ | ☐ 全屏 ☐ 无边框窗口 | ☐ 可用 ☐ 不可用 | |
| ______ | ☐ 全屏 ☐ 无边框窗口 | ☐ 可用 ☐ 不可用 | |
| ______ | ☐ 全屏 ☐ 无边框窗口 | ☐ 可用 ☐ 不可用 | |

**补充测试**：换几组不同的键位（F1 / F12 / 小键盘 / `\` / 组合键），看是否有某些键更不容易被吞。

### 判定

| 结果 | 行动 |
|---|---|
| 主力游戏全屏下可用 | ✅ 热键方案成立 |
| 只有无边框窗口可用 | ⚠️ 需在引导里建议用户改用无边框窗口 |
| 全部不可用 | 🔴 **启动预案**：手机遥控 / Stream Deck（见产品设计 §6.5），产品设计需要调整 |

## 6. 实验 5：长时间稳定性

**目的**：验证核心音频链路长时间运行不会退化。

| 步骤 | 操作 |
|---|---|
| 1 | 保持链路，循环播放音频 |
| 2 | 持续 **2 小时** |
| 3 | 期间定期让队友确认音质 |

**观察点**：
- ☐ 是否出现周期性爆音 / 咔哒声（→ 时钟漂移问题）
- ☐ 音质是否随时间长逐渐变差
- ☐ 延迟是否逐渐增大
- ☐ 是否出现无声（需要重启才恢复）

> 这一项直接验证技术设计 §2.3 的时钟漂移风险是否真实存在。

## 7. 判定汇总

| 假设 | 结论 | 证据 |
|---|---|---|
| **H1** 降噪不吃音频 | ☐ 成立 ☐ 部分成立 ☐ 不成立 | 实验 2 数据表 |
| **H2** 热键在游戏中可用 | ☐ 成立 ☐ 部分成立 ☐ 不成立 | 实验 4 数据表 |
| **H3** macOS 26 上链路可通 | ☐ 成立 ☐ 不成立 | 实验 1 数据表 |
| 混音架构可行 | ☐ 成立 ☐ 不成立 | 实验 3 |
| 长时间稳定 | ☐ 成立 ☐ 不成立 | 实验 5 |

### 决策规则

| 情况 | 决定 |
|---|---|
| **H1 ✅ + H2 ✅ + H3 ✅** | **GO** —— 直接进入 M1 开发 |
| H1 ✅ + H2 ❌ | **GO，但改设计** —— 把手机遥控提到 P0，热键降级为辅助 |
| H1 ⚠️（只有关降噪才能听清） | **GO，但重定义产品** —— "自动配置引导"从差异化功能升级为**核心功能**，且要做更强的电平优化 |
| H1 🔴（怎么都听不清） | **NO-GO** —— 停下来，重新思考产品形态（例如转向"本地监听/直播"场景） |
| H3 ❌（VB-CABLE 在 macOS 26 不可用） | **改路线** —— 直接跳到自研 AudioServerPlugIn（阶段 2 提前），用 libASPL 做最小验证 |

## 8. 如果 H1 失败：三个备选方向

万一队友那边怎么都听不清，不要急着放弃，先试这三条：

| 方向 | 做法 | 代价 |
|---|---|---|
| **A. 让用户能关别人的降噪** | 把"关闭降噪"的引导做到极致，做成核心功能 | 依赖用户配合，转化率受损 |
| **B. 音效"拟人化"处理** | 对音效做动态处理（压缩、瞬态增强），让它更像人声、更不像稳态噪声 | 音质受损，且不保证有效 |
| **C. 换场景** | 从"游戏开黑"转向"直播 / 会议整活 / 语音房"——这些场景的降噪策略可能更宽松 | 改变目标市场 |

**建议顺序：先 A，再 B，最后才考虑 C。**

## 9. 时间安排

| 时段 | 内容 |
|---|---|
| 第 1 小时 | 装 VB-CABLE、准备测试素材、打通链路（实验 1） |
