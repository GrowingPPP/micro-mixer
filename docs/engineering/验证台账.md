# 验证台账

**这份文件回答一个问题：每条结论背后的证据，到底有多强？**

为什么需要它：本项目开发中反复出现同一类失误 —— **结论比证据强**。
例如"关窗后引擎继续跑"曾经只验了"进程还活着"就写成了结论；
"输入音频正常"曾经只在终端启动下验过（而用户永远是双击启动）。
把证据强度摊开写清楚，才能知道哪些可以信、哪些还得再验。

**证据等级**（从强到弱）：

| 等级 | 含义 |
|---|---|
| **A** | 端到端实测：从真实设备量回来（录音验频、环回验证） |
| **B** | 进程内实测：真实运行路径跑通并断言了关键量 |
| **C** | 状态断言：命令返回成功 / 状态字段正确（**不代表真的出声**） |
| **D** | 未验证 |

- **B（进程内 PCM、可控后端与离线实测）**：

## 2026-10-22：变声器第一阶段引擎集成回归

## 修过的"只在某条路径下才坏"的问题

这类问题最隐蔽 —— **换个入口就换个结果**。本项目已经踩到三次：

| 问题 | 只在哪条路径下坏 | 根因 |
|---|---|---|
| 麦克风没权限 | **双击启动**（终端启动会继承终端的权限） | Info.plist 缺 `NSMicrophoneUsageDescription` |
| 热键不响应 | **命令行**（GUI 有 tao 的事件循环） | 主线程没跑应用事件循环 |
| **监听没声音** | **热键 / 手机遥控**（界面点击正常） | 监听只挂在界面点击那条路上，另两条直接调 `PlaybackControl::play` 绕过了它 |
| **手工挑的音效列表被目录全量替换** | **每次打开 App** | 前端只要配置里有 `dir` 就重新扫目录，把 `sound_files` 覆盖掉 |
| **`monitor_device` 被抹掉** | **每次点「启动」** | 前端写死 `monitor_device: null`；且字段名误用驼峰（serde 只认蛇形，驼峰被静默忽略） |
| **点「二维码」没反应** | **运行中**（停止后就"自己出现了"） | 二维码面板被放在**设置区内部**，而运行时会折叠设置区 —— 点击其实生效了，只是藏在一个看不见的容器里 |

**教训 1：一个功能有多条触发路径时，每条都要单独验。**
**教训 2：GUI 每次「启动」都会把配置回写一遍 —— 任何"前端没原样带回去"的字段都会被悄悄抹掉。**
新增配置项后要做一次**全字段往返审计**：手工写一份设满所有字段的配置 → 启动 GUI → 对比回写结果。 监听的整个意义就是游戏内用热键时的反馈，
而它恰好在热键路径上不生效 —— 等于白做。

### 补一条：每次重新签名都会让麦克风权限重新弹窗

`build-app.sh` 每次都会 ad-hoc 重新签名，而 **TCC 权限是绑定代码签名的** ——
所以每次重新打包后，第一次启动系统都会**重新弹一次麦克风授权**。

**在弹窗还没被处理时，前端不会加载**（表现是窗口空白、后端日志里只有"菜单栏 图标已创建"，
一个字都不多）。人用的时候点一下「允许」就过去了，但**自动化脚本会一直等下去**。

> 排查这个坑花了很久，因为没有控制台 —— 为此加了一条**前端错误上报通道**：
> 前端把 JS 异常通过 `js_error` 命令送回后端，`open --stdout <文件>` 就能看到。
> 打包后的 App 出问题，这是唯一的窗口。

### 补一条：UI 状态组合也要验

上面那条"点二维码没反应"是**用户发现的**，不是我自己验出来的。原因是我的界面预览
**只渲染过"设置区展开"的状态**，从没渲染过"运行中 + 设置区折叠"这个组合 ——
而用户实际就处在这个组合下。

**教训 3：界面预览要覆盖真实的状态组合，不能只渲染一个默认状态。**
（二维码这类"能不能看见"的问题，只能靠渲染出来看；单元测试和冒烟测试都抓不到。）

## 已知的外部问题（不是本程序的 bug，但会影响使用）

### 虚拟声卡偶发异常

「豆包会议记录虚拟设备」约 **15 次开流出现 1 次**异常，已观察到两种表现：

1. **音高翻倍**（880Hz → 1731Hz）
2. **环回拿不到信号**（全零）

**定位依据**：同一次运行里同时抓两份数据 —— 引擎交给声卡的原始 f32 是 **878.9 Hz**，
设备环回录回来的是 **1731.4 Hz**；幅度一致、播放速率正常、协商格式无警告。
**结论：引擎侧正确，问题在虚拟声卡那一层。**

**处理**：自检会自动重开流重试最多 3 次；仍失败则提示排查方向。

> ⚠️ 该故障出在「豆包会议记录虚拟设备」上。换用 VB-CABLE（M1-00，尚未做）后需重新确认。

### macOS 权限

- 麦克风权限**必需** `NSMicrophoneUsageDescription`，缺了系统直接拒绝（表现是录音全零）
- **TCC 权限绑定代码签名**：`tauri build` 合并 plist 后原签名失效，必须重新 ad-hoc 签名
- 所以打包要走 `apps/mixer-gui/build-app.sh`，**不要直接 `tauri build`**
- ⚠️ **每次重新打包（ad-hoc 重签）后，第一次启动会重新弹麦克风授权**。
  弹窗没被处理时**前端不会加载**（窗口空白、日志里只有"菜单栏 图标已创建"）。
  别再把这个症状误判成别的原因 —— 见下面那条撤回记录。
- ✅ **已澄清（第三次才对）**：权限要求**取决于签名方式**。
  - **ad-hoc**（不开强化运行时）：只要 `NSMicrophoneUsageDescription`；目录声明不需要。
  - **真证书 + 强化运行时**（`--options runtime`）：麦克风除了 Info.plist 还要
    **`com.apple.security.device.audio-input` entitlement**（缺了**静默录到零**，
    peak 精确 −100）；读 `~/Downloads` **必须**有 `NSDownloadsFolderUsageDescription`
    （缺了文件读取**永久阻塞**，表现为"点启动没反应"）。
  - 前两次结论（"加声明会坏" → "撤回，其实是弹窗"）都是**在 ad-hoc 下观察的**，
    所以看不到强化运行时的要求。见 README 里那节「签名方式会改变权限行为」。
- 🪟 **打包后的 App 没有控制台**，前端 JS 异常完全静默 —— 已加 `js_error`
  上报通道（JS 异常送回后端，`open --stdout <文件>` 可见）。
