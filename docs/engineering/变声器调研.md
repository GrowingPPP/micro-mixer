# 变声器调研

> 范围：在「麦克风混音助手」的实时麦克风链路上增加人声变换（变声）能力需要什么。
> 本文只做调研，不给出实现代码；数据流与伪代码仅用于说明插入点和参数语义。
> 产品当前明确定位「不是变声器」（见[项目上下文](../ai/PROJECT_CONTEXT.md)），增加此功能会改变产品定位与文档表述，需先做产品决策再动手。

---

## 1. 结论摘要

1. **变声只应作用于「真实麦克风人声」路径**，不进入音效解码、正式播放、试听、监听的素材链路。插入点推荐在**漂移控制重采样之后、写入环形缓冲之前**：输出采样率固定，漂移控制与环形水位语义不变，前视限幅与电平表自然看到变声后信号。
2. **延迟是第一约束，不是 CPU。** 现有链路已引入约 20–60 ms（采集缓冲、环形水位、限幅前视、虚拟设备 IO）。变声算法本身可能再加很大一块：Signalsmith Stretch **默认预设的分析块约 100–120 ms**（`presetDefault` 为 0.12×sr 块 + 0.03×sr 步进，`presetCheaper` 为 0.1×sr + 0.04×sr），其 `inputLatency`/`outputLatency` 处于数十至上百毫秒量级；纯 Rust 的 `pitch_shift` 固定延迟约 `1024 − out_samples` 样本（约 19–21 ms）。当前产品**监听流不送人声**（监听侧麦克风增益被置为静音），因此对方听到的变声延迟叠在网络抖动缓冲之后，一般可接受；**若产品要增加「自己听到变声效果」**，端到端自听延迟必须控制在约 20–30 ms 内，频域大窗算法做不到，需要明确取舍。
3. **许可证决定技术选型，延迟决定配置。** 本仓库是 MIT。Rubber Band（GPL / 商业双授权）、SoundTouch（LGPL）、tdpsola（AGPL）都会给闭源分发带来合规负担；**MIT 的 Signalsmith Stretch** 同时提供独立音高与共振峰控制，是当前最匹配的算法库，**但它的默认预设块长约 100–120 ms**，用于实时麦克风必须改成更小的块并实测。Rust 包装没有暴露上游 `configure()`，而是用 `Stretch::new(channel_count, block_length, interval)` 在创建时配置。纯 Rust 的 `pitch_shift` 可做约 20 ms 级的极简音高移位，但没有共振峰控制。
4. **功能形态分级明确。** 音高 + 共振峰（含性别感、年龄感预设）适合实时麦克风；机器人音、混响、和声、降噪是可叠加的效果器；**神经网络音色克隆（RVC 等）不适合本产品当前的低延迟实时约束**（公开端到端延迟约 170 ms，且引入 Python/PyTorch 或大型推理运行时）。
5. **改动是「共用层加一条人声处理链」，不是新做一套引擎。** `audio-core` 增加人声处理模块并挂在采集侧，`app-config` 持久化参数，`audio-session` / GUI / CLI / 热键 / 遥控按需暴露开关与预设。音效播放门控、单音效约束、试听与监听互斥语义都不应被改变。
6. **产品定位与文档是显性成本。** 需要同步修改「不是变声器」的表述、README 功能说明、商业文档里把「变声」列为付费点的描述，并重建 `THIRD-PARTY-NOTICES.md`。

## 2. 功能形态：哪些适合实时麦克风链路

| 形态 | 典型做法 | 是否适合本产品实时麦克风 | 说明 |
|---|---|---|---|
| 音高偏移（pitch shift） | 频域移调 / 时域同步叠加 | 适合 | 核心能力；常与共振峰一起构成「变声」体感 |
| 共振峰 / 音色（formant shift） | 包络搬移、源-滤波、WORLD 谱包络 | 适合，但是难点 | 决定「像男/像女/像小孩」，只改音高会像花栗鼠 |
| 性别感转换 | 音高 + 共振峰 + 少量频谱倾斜 | 适合 | 本质是预设，不是独立算法 |
| 机器人音 / 对讲机 | 环形调制、载波钉死、带通、失真 | 适合 | 纯时域效果器，延迟几乎为零 |
| 混响 / 空间 | FDN、卷积、Schroeder | 适合（作效果） | 注意会增加峰值与「回声感」，与远端回声消除叠加要小心 |
| 和声 / 齐唱 | 多路移调叠加 | 有条件适合 | 多一条移调链即多一份 CPU 与延迟；建议只做 1–2 声部 |
| 降噪 | RNNoise 类谱减 / 门限 | 适合，但应视为独立功能 | 与变声正交；可先可后 |
| 预设（女声、小孩、机器人…） | 参数包 | 适合 | 商用变声器的主流交互 |
| 音色克隆 / 神经变声 | RVC、DDSP、流式 VC | 当前不适合 | 延迟、体积、模型管理、许可证与「低延迟语音」目标冲突 |

不适合挂在麦克风路径上的：**任何需要离线整段分析的算法**（部分高质量 WORLD / 高质量相位声码器配置）、**需要 GPU 才能跑实时的模型**、**会改动音效素材本身的处理**（音效应在控制侧解码后原样播放，用户买的音效不应被变声染色）。

商用参考（形态组织方式，不是技术依赖）：

- Hatsumi 的链路是 `麦克风 → 环形缓冲 → 噪声门 → Rubber Band 音高/共振峰 → 效果链（EQ / 环形调制 / 软削波 / 混响）→ 虚拟设备`，预设用 TOML 描述 `semitones + formant_scale + effects`（[Hatsumi README](https://github.com/rohitdevsol/hatsumi)）。
- Mimik 同样以 Rubber Band 做音高与共振峰，音色用 TOML 描述（[Mimik README](https://github.com/subhdotsol/mimik)）。
- Voicemod 等商业产品的公开定位是「变声为主、soundboard 为辅」（见本仓库[产品方案](../product/产品方案-Windows与macOS.md)的竞品表），与本产品「音效板为核心」的定位相反——增加变声要避免把产品叙事拉过去。

## 3. 算法对比

延迟量级按 48 kHz、常见配置估算，用于排序比较；具体实现差异很大，最终以目标库的 `latency` 查询和实测为准。

| 算法 | 典型算法延迟 | CPU | 音质 | 音高/共振峰独立 | 实时麦克风 |
|---|---|---|---|---|---|
| 仅改变重采样率（resampling） | 低（插值/多相滤波群延迟，约 0–5 ms） | 极低 | 只能整段变调且时长变化；做「常时长变调」需再拼接 | 否（速度音高绑定） | 只适合极轻效果 |
| 粒度 / OLA / SOLA / WSOLA | 窗长量级，约 5–20 ms | 低 | 语音尚可，易有颗粒感、金属声 | 否（保音高变时长；变调要叠加重采样） | 可用，音色控制弱 |
| TD-PSOLA | 基频周期级，约 5–15 ms | 低–中 | 单音源语音质量高，**天然保共振峰** | 是（音高改变时共振峰基本保留） | 适合语音，需可靠基频 |
| 相位声码器（phase vocoder） | 窗长/合成窗量级，约 20–120 ms（默认大窗可达 100+） | 中 | 泛用、可多音源；有相位涂抹与颤音 | 可做频率映射，独立共振峰需额外包络处理 | 可用，但必须自选小窗并接受音质下降 |
| 源-滤波 / 共振峰搬移 | 分析帧量级，约 10–30 ms | 中 | 只改音色不改音高时质量好 | 是（正交控制） | 适合，常与移调串联 |
| WORLD（Harvest/CheapTrick/D4C） | 帧移量级，可做到几十 ms | 中–高 | 语音再合成质量高，参数完全分离 | 是（F0 与谱包络独立） | 可实时，但要仔细控制分析帧与 CPU |
| 神经网络变声（RVC 等） | 公开端到端约 170 ms（ASIO 约 90 ms）；研究/专用实现约 32–70 ms | 高（GPU 或强 CPU） | 音色相似度最高 | 视模型而定 | 边界可用，依赖与体积都重 |

### 3.1 各算法要点与依据

**重采样变调。** 直接改变播放速率即可变调，代价是时长同步变化；插值核极短时延迟可以忽略。这是 `LinearResampler` 已有能力的延伸，但不能单独构成「变声」。

**OLA / SOLA / WSOLA。** 把信号切成重叠片段、按相似度拼接来改变时长；再叠加重采样可变调。窗长决定延迟与颗粒感。WSOLA（Verhelst & Roelands）是语音时长规整的经典方法，文献与教材中广泛使用。

**TD-PSOLA。** 按基频周期切片后重叠相加，改变拼接疏密即可改音高且**保留声道共振峰**，所以男声变女声这类任务里「不会变花栗鼠」。代价是依赖可靠基频估计；音乐、多人说话会退化。tdpsola 实现明确声称 formant-preserving（[tdpsola](https://codeberg.org/PieterPenninckx/tdpsola)）。

**相位声码器。** STFT → 改频率轴映射（移调）或改相位推进（变时长）→ 逆变换。延迟主要来自分析/合成窗；加相位锁定（identity phase locking）可减轻「相位涂抹」。Signalsmith Stretch 的公开方法论来自 ADC22 演讲 *Four Ways To Write A Pitch-Shifter*（[Signalsmith Stretch](https://signalsmith-audio.co.uk/code/stretch/)），并提供 tonality limit 与自定义频率映射以部分保留音色。Rubber Band 的技术说明称其为「带打击瞬态相位重置、自适应伸缩比与相位层压的块式相位声码器」，移调用「先伸缩后（或前）重采样」组合实现（[technical notes](https://breakfastquay.com/rubberband/technical.html)）——说明这一类库的核心仍是相位声码器，差别在工程细节。

**重要实测/源码事实：** Signalsmith Stretch 的默认预设不是为超低延迟麦克风设计的。上游头文件中 `presetDefault` 配置为 `block = 0.12×sampleRate`、`interval = 0.03×sampleRate`，`presetCheaper` 为 `0.1×sr` 与 `0.04×sr`（[signalsmith-stretch.h](https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/signalsmith-stretch.h)）。也就是说默认分析块约 100–120 ms。要压进实时麦克风预算，必须自选更小的块/步进并**实测音质**：上游用 `configure()`，Rust 包装用 `Stretch::new(channel_count, block_length, interval)`（`new` 直接传给底层创建函数，`process()` 不再读取块长）。上游 README 也提醒 Debug 构建可慢至 10 倍，且 `splitComputation` 会再加一个 interval 的输出延迟。

**流式接口的关键细节：** `signalsmith-stretch` 的 `process(input, output)` 允许输入帧数与输出帧数不同（这是伸缩能力本身）；Rust 包装只借出切片，不在调用内分配，输入输出均要求交错且长度能被声道数整除（仅 `debug_assert` 检查）。因此不能把它当作“原地处理固定块”的节点：采集回调必须准备预分配的输入/输出 FIFO，按算法实例的块长喂入，再按环形缓冲当前需要的帧数取出。开启、切预设或改变块长都要重置实例并处理残余尾部，否则会丢帧或产生延迟跳变。

**共振峰 / 性别转换。** 只改音高时声道长度印象不变，听感像「加速播放」。性别感主要由前几个共振峰位置决定，需要在移调之外把频谱包络向相反方向搬移。Signalsmith Stretch 提供 `setFormantFactor` 与 `compensatePitch`（[上游 README](https://github.com/Signalsmith-Audio/signalsmith-stretch)），并明确指出其共振峰修正**不如 PSOLA 这类单音源算法锐利**，且需要粗略基频。

**WORLD。** 把语音拆成 F0、非周期性、谱包络三套可独立编辑的参数，再合成；因此理论上音高与共振峰完全解耦。上游仓库说明「无算法专利」，许可证为 modified-BSD，标题即面向 real-time applications，并有 sequential real-time 生成器相关工作（[mmorise/World](https://github.com/mmorise/World)）。Rust 侧有 `rsworld` / `Rust-WORLD` 包装，但需要确认实时流式接口与回调内分配行为。

**神经网络变声（RVC 等）。** 用训练模型迁移音色，相似度远超经典 DSP。RVC 官方 README 给出的端到端延迟为 **170 ms**，使用 ASIO 输入输出时约 **90 ms**，且「高度依赖硬件驱动」（[RVC README](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI)）。仓库自带 `realtime_gui.py` 与 VST，属于 Python/PyTorch 生态；引入 Rust 桌面应用意味着 ONNX/ort 或 Torch 推理运行时、模型文件分发、GPU/线程管理。少数工作把延迟压得更低：Google StreamVC 论文报告在手机单核 CPU 上端到端约 70.8 ms（[arXiv:2401.03078](https://arxiv.org/abs/2401.03078)）；Beatrice 项目宣称 CPU 单线程约 50 ms 且带独立音高与共振峰（[prj-beatrice.com](https://prj-beatrice.com/)）。这些说明「神经变声能实时」但**不是本产品当前打包与延迟预算的形态**。

**降噪（RNNoise）。** 小型 GRU 预测 Bark 带增益，约 10 ms 前视，无 GPU，x86 上约 60× 实时，模型仅 85 kB，BSD 许可（[RNNoise](https://jmvalin.ca/demo/rnnoise/)）。适合做「人声清晰」而不是「变声」；Rust 生态有 `nnnoiseless`（BSD-3-Clause）。

### 3.2 延迟预算视角

现有产品文档给出的额外延迟约 20–60 ms（[技术设计-音频架构与驱动](技术设计-音频架构与驱动.md)）。语音通话端到端常见 100–300 ms。

| 场景 | 新增变声延迟 | 可接受性 |
|---|---|---|
| 只影响对方听到的声音（现状：监听不含人声） | 小窗配置 +20–50 ms；默认大窗配置 +80–150 ms | 小窗一般可接受；默认预设偏大，会明显吃掉通话预算 |
| 自己要听到变声后的自己 | 需端到端 ≲ 20–30 ms | 大窗频域算法不合格；只能用极短窗 / 时域算法，或干脆不做自听 |
| 自己听原声、对方听变声 | 可拆分 | 产品体验清晰，实现上监听流继续不送人声即可 |

**建议默认：保持「监听不含人声」的现状语义**，变声只影响送往虚拟麦克风的转发信号。若将来要做「变声试听」，应作为独立输出并单独评估延迟，而不是塞进现有监听流。算法选型时要把「默认预设延迟」与「目标配置延迟」分开写进验收，不能只引用库名。

## 4. Rust 方案对比

许可证以 crates.io 声明与上游 LICENSE 为准；「实时安全」按是否能在已分配缓冲上 `process()`、不在回调中分配/加锁/文件 IO 来评估。项目要求见[共用模块开发约定](../../crates/AGENTS.md)。

| 方案 | 许可证 | 维护/活跃 | 实时安全 | 音高/共振峰独立 | 跨平台 | 打包影响 | 结论 |
|---|---|---|---|---|---|---|---|
| **signalsmith-stretch**（上游 C++）+ **signalsmith-stretch** crate（colinmarc） | MIT | 上游活跃，官方 README 点名该 Rust 包装 | `process` 借出切片、不在调用内分配；输入/输出帧数可不同，外层需预分配 FIFO | **是**（transpose + formant + compensatePitch） | macOS（AppleClang）/ Windows（MSVC）为主 | 捆绑 C++ 子模块，`cc` + bindgen 编译，静态链入；无动态库分发 | **音质与共振峰首选**；但必须用 `new()` 自配小块以控延迟，默认预设偏大；C++ 构建会影响 macOS 上的 Windows 交叉检查 |
| **ssstretch**（另一 Rust 绑定） | MIT | 2025 年后较少更新 | 待核 | 待核（同上游能力） | 同上 | 同上游 | 备选包装 |
| **pitch_shift**（纯 Rust 相位声码器） | MIT | 仍在更新 | 固定 128 样本块、固定延迟 `1024 - out_samples`（约 19–21 ms） | **否** | 纯 Rust，无 C 工具链 | 最轻 | 极简、低延迟音高移位可用；无法做性别感 |
| **rubberband** / **rubberband-sys** | **GPL-2.0-or-later**（商用需购买） | 上游活跃 | 实时 API 完整 | **部分**（`OptionFormantPreserved` 保共振峰；独立 formant 比例需 R3） | 跨平台 | C++；GPL 传染 | **与 MIT 产品分发冲突**，除非购买商业授权 |
| **soundtouch** / **soundtouch-ffi** | **LGPL-2.1** | 长期维护 | 官方称支持实时；流延迟最大约 100 ms | 音高与速度独立；**共振峰未证实** | 跨平台 | C++；LGPL 对静态链接有再链接义务 | 延迟偏大 + 许可证负担，不推荐 |
| **rsworld** / **Rust-WORLD** | 包装 MIT；WORLD 本体 modified-BSD | 一般 | 待核（分析/合成多为块式） | **是** | 跨平台 | C/C++ 源编译 | 共振峰解耦最强，适合「完整」档做音色；实时流接口要验证 |
| **tdpsola** | **AGPL-3.0** | 2020 年后停更 | 待核 | 声称保共振峰 | 纯 Rust | 无 C | 许可证直接排除 |
| **nnnoiseless** | BSD-3-Clause | 维护中 | 可流式 | 不适用（降噪） | 纯 Rust | 无 | 降噪可选件 |
| **fundsp** / **dasp** / **fon** | MIT / Apache | 活跃 | 面向节点图与通用 DSP | 无完整变声实现 | 纯 Rust | 无 | 适合做效果器（EQ、软削波、混响、环形调制），不能替代移调/共振峰 |
| **mimik-dsp**（MIT） | MIT | 新，样本极少 | 待核 | 参考实现 | macOS 向 | 依赖 rubberband | 可读源码取经，不宜直接依赖 |
| RVC / 本地神经 VC | 项目多为 MIT，但生态是 Python/Torch | 活跃 | 批处理为主 | 隐式 | 需推理运行时 | 体积、模型、GPU | 实验性，不适合首发 |

补充核对结果（crates.io 元数据，2026-10）：

- `signalsmith-stretch` 0.1.3，MIT，仓库 [colinmarc/signalsmith-stretch-rs](https://github.com/colinmarc/signalsmith-stretch-rs)；API 含 `new(channel_count, block_length, interval)`、`preset_default` / `preset_cheaper`、`set_transpose_factor(_semitones)`、`set_formant_factor(_semitones)`、`signalsmith_stretch_set_formant_base`、`input_latency` / `output_latency`、`process`、`exact`、`flush`。没有暴露上游 `configure()`。
- 上游 [Signalsmith-Audio/signalsmith-stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch) 为 MIT、C++11 头文件库；`splitComputation` 可把谱计算摊开（代价是多一个 interval 的输出延迟），适合严格实时回调；README 明确 Debug 构建可慢至 10 倍。当前 `signalsmith-stretch` Rust 包装只暴露 `new()` 的块长/间隔配置，没有暴露 `splitComputation`，不能把它当作首发可直接使用的选项。
- `pitch_shift` 2.1.0，MIT，[NathanRoyer/pitch_shift](https://github.com/NathanRoyer/pitch_shift)：纯 Rust 相位声码器，需按 128 样本喂入，延迟固定。
- **spike 观察**：`pitch_shift` 2.1.0 在 FFT bin 恰为 `(0, 0)` 时，相位提取会产生 NaN，并永久污染内部相位状态。触发条件是参与相位计算的 bin 实部与虚部同时为零；本轮 30 秒谐波人声输入未触发。`tools/voice-spike` 的包装层在输出出现非有限值时清零该块并重置根状态（不重新分配），同时统计恢复次数；因此 spike 的基准与音质结果代表「pitch_shift + 恢复层」，不是纯上游行为。macOS 30 秒基准的 3 个回调粒度下恢复次数均为 0，不能据此认为问题不存在或恢复层无需保留。
- `rubberband` 0.1.5 / `rubberband-sys` 0.1.4：GPL-2.0-or-later；上游双授权（GPL 或商业），见 [breakfastquay.com/rubberband](https://breakfastquay.com/rubberband/)。
- `soundtouch` 0.5.4 / `soundtouch-ffi` 0.4.1：LGPL-2.1；官方称流延迟最大约 100 ms（[SoundTouch](https://www.surina.net/soundtouch/)）。
- `rsworld` 0.1.0、`Rust-WORLD` 0.1.1：MIT 包装。
- `tdpsola` 0.1.0：AGPL-3.0。
- `nnnoiseless` 0.5.2：BSD-3-Clause（[jneem/nnnoiseless](https://github.com/jneem/nnnoiseless)）。

**依赖引入的项目义务**：更新 `Cargo.lock`，并用 `python3 tools/gen-third-party-notices.py` 重建 `THIRD-PARTY-NOTICES.md`（该脚本只收 macOS 目标下 normal/build 可达依赖）。若捆绑 Signalsmith 的 C++ 子模块，需确认 LICENSE 文本能被脚本收进声明；必要时手工补上游版权声明。

## 5. 本项目集成点与改动清单

### 5.1 插入位置（数据流）

现状主路径（[项目上下文](../ai/PROJECT_CONTEXT.md)、`audio-core` 的采集/渲染处理）：

```
真实麦克风 → 下混单声道 → 漂移控制重采样 → 环形缓冲 → 与音效混音 → 前视限幅 → 电平表/输出
                └─ CaptureProcessor ──────────────┘   └─ RenderProcessor ──┘
音效：控制侧解码 → 预准备到输出采样率 → 播放器渲染 ──┘
监听：独立输出流，仅音效（麦克风增益被置为静音）
试听：独立工作线程，仅音效
```

建议插入：

```
真实麦克风 → 下混单声道 → 漂移控制重采样 → [人声变换] → 环形缓冲 → 与音效混音 → 前视限幅 → 输出
```

伪代码（仅表达顺序与约束）：

```
capture_process(interleaved_in):
    downmix_to_mono()
    drift_resample_to_output_rate()      # 现有逻辑，保持不变
    voice_transform.run(fixed_block)     # 预分配工作区，不在回调内分配
    push_to_ring_stereo_duplicate()      # 现有逻辑
```

为什么放在重采样**后**：

- 变声参数（半音、共振峰比例）定义在**输出采样率**上，跨 44.1k/48k 设备时听感一致；
- 漂移控制仍只服务「麦克风时钟 ↔ 虚拟设备时钟」，不被变声内部块大小干扰；
- 前视限幅器看到的是最终要送出的人声，过冲保护语义不变；
- 电平表量的是「限幅之后、真正送出去的信号」，自然包含变声结果，与文案一致。

不推荐放在渲染侧读环之后：将来若增加人声监听或第二消费者会重复处理，且环形缓冲里存的将是「未变声」数据，与「对方听到什么」不一致。

### 5.2 语义澄清（需要产品拍板的问题）

| 问题 | 建议默认 | 理由 |
|---|---|---|
| 重采样前还是后插入 | 后 | 见上 |
| 是否影响漂移控制 | 否 | 漂移只管时钟，不管音色 |
| 监听是否听到变声后的人声 | **否，维持现状** | 现状监听流麦克风增益为静音；变声不应把监听语义改成「人声监听」 |
| 是否需要「变声试听」 | 可后置 | 若做，单独短时回环，不要改监听流 |
| 待机（关闭音效）时是否仍变声 | **是** | 待机语义是「麦克风继续转发」，人声处理属于转发路径 |
| 电平表 / 自检是否受影响 | 电平表随转发信号变化；自检不受影响 | 自检是独立流与独立缓冲，不经过混音引擎 |
| 校准麦克风是否受影响 | 校准测量的是混音输出峰值 | 变声（尤其混响、削波）会改变峰值；建议校准期间旁路变声，或提示关闭后再校准 |
| 配置如何持久化 | `app-config` 新增人声节，默认关闭 | 与 `mic_gain_db` 等同样走 TOML；旧配置无此节时视为关闭 |
| 热键 / 手机遥控是否切换预设 | 首发可不做；完整档再加 | 现有热键语义是「绑定音效槽位」，扩展前要定冲突与文案 |
| CLI 是否暴露 | 最小可用：`config` 读写即可；完整档加参数 | 与 GUI 共用配置 |
| GUI 面板位置 | 「混音控制」区增加「人声效果」折叠组；预设管理放「连接设置」 | 与麦克风音量同属人声链路，避免和音效库抢主区域 |

### 5.4 参数与预设（建议模型）

预设 = 参数包，而不是「加载一个模型」：

- `pitch_semitones`：音高（半音）
- `formant_ratio` 或 `formant_semitones`：共振峰（可选是否补偿音高）
- 效果开关：噪声门、EQ、软削波、环形调制（机器人）、混响
- `enabled`：全局旁路（旁路时零延迟直通）

参数更新约束：**半音、增益类可在回调内原子更新并平滑**；块大小、算法实例切换必须走已有的无锁命令队列模式，且实例在非实时线程预分配。可参考现有 `QueuedCommand` / `AtomicF32` 的做法。

## 6. 平台差异

| 方面 | macOS（CoreAudio） | Windows（WASAPI） |
|---|---|---|
| 设备与缓冲 | IOProc 周期由设备/聚合设备决定；缓冲在设置里已有 `buffer_ms` | 共享模式下引擎周期固定，客户端无法把周期调得比引擎更小；缓冲需容得下引擎与客户端两次处理（[IAudioClient::Initialize](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-initialize)） |
| 额外延迟 | 现有设计约 20–60 ms（采集、水位、限幅、虚拟设备） | 同量级；VB-CABLE 环回与目标应用缓冲另计 |
| 低延迟手段 | 调小设备缓冲；避免聚合设备额外安全偏移 | 事件驱动共享流；ASIO 不在本产品路径内（RVC 的 90 ms 依赖 ASIO，不能直接类比） |
| C/C++ 打包 | `cc` 静态编入；签名与 entitlement 不因静态库改变 | 静态编入；若改为 DLL 需随安装包分发并注意代码签名 |
| CPU 调度 | 音频线程由 CoreAudio 提升优先级；仍禁止在回调分配 | 同样禁止回调分配；WASAPI 客户端线程周期不匹配会增加延迟（见上） |
| 新权限 | **不需要新权限**（仍只是麦克风 + 用户选择的目录） | 无新权限；WebView2 与虚拟声卡引导不变 |
| 交叉检查 | 本地 `cargo check` | `tools/win-cross-check.sh` 目前用 `llvm-rc` 桩跑 `--target x86_64-pc-windows-msvc`；新增 C++ 依赖后 `cc` 会尝试调用 MSVC `cl.exe` 编译包装层，macOS 上没有该编译器。要么为该脚本补一个受控的 C++ 编译桩，要么改用不依赖 C/C++ 的纯 Rust 方案，不能把交叉检查失败误报成代码缺陷 |

结论：**平台差异主要体现在缓冲与调度，不体现在变声算法本身**；算法层选静态链接的纯源码库即可，避免动态库签名与 DLL 捆绑。Windows CI 离线基准已通过，但 Windows 仍未真机验收；变声功能不能用 macOS 或 CI 离线结果替代 Windows 真机验收。

## 7. 风险与未决问题

### 7.1 风险

1. **实时安全。** 变声算法内部若在 `process()` 里分配、加锁或做 FFT 临时缓冲，会造成爆音。必须沿用「回调内不分配、不加锁、不做文件 IO」，并在音频回调的 `catch_unwind` 保护下运行。CI/测试里可用项目已有的 TrackingAllocator 风格检查捕获回调分配。
2. **延迟叠加。** 算法窗长 + 现有水位 + 限幅前视 + 虚拟设备 IO 可能轻易超过 100 ms（Signalsmith 默认预设一项就可到百毫秒级）。对「对方听」通常尚可，但若用户打开系统监听或录音软件内放，会听到明显回声感。验收必须量测端到端延迟，不能只跑音质听感。
3. **音质。** 大幅移调（±12 半音以上）相位声码器易有颤音与涂抹；共振峰修正不如 PSOLA 锐利；机器人/混响会降低语音清晰度，可能触发对方语音软件的降噪（产品已有「74 dB 问题」讨论，见[产品方案](../product/产品方案-Windows与macOS.md)）。
4. **CPU 峰值。** 频域算法偶发整块谱计算；上游 `splitComputation` 可以少量延迟换平坦负载，但 Rust 包装未暴露。需要在目标机器上测「变声开启时 render/capture 回调耗时」的 P99 与单次最坏值，而不只看平均。
5. **反馈与啸叫。** 变声本身不引入新反馈回路，但若用户用外放 + 麦克风，混响与增益会放大啸叫风险；文档应提示。现有监听不含人声，**降低了**耳机啸叫概率，这是保持该语义的理由之一。
6. **与试听 / 监听的互斥关系。** 试听只播音效、监听只同步正式音效——变声不得进入这两条路径，否则会破坏「单音效」与「试听仅自己可听内容」的产品约束。
7. **Windows 真机未验收与构建链路。** Windows CI 离线基准已能完成构建并跑通 27 个用例，但任何「macOS 已测」或 CI 离线结论都不能替代 Windows 真机；新增 C++ 构建还可能踩 MSVC 编译差异（Signalsmith README 提到 AppleClang 16 与 `-ffast-math` 的坑）。`signalsmith-stretch` 的 Rust 包装通过 `cc` + bindgen 在构建期编译 C++，而 `tools/win-cross-check.sh` 在 macOS 上检查 MSVC 目标：`cc` 需要 `cl.exe`，现有 `llvm-rc` 桩不覆盖这一步。引入前必须先决定交叉检查策略，否则现有的 Windows 门禁会直接失效。
8. **许可证。** GPL/LGPL/AGPL 方案要么换库，要么购买商业授权并改分发条款；MIT 产品不应静默引入 GPL。Rubber Band 商业授权为一次性买断（约 £590 含署名 / £1,490 小团队免署名 / £9,320 十人以上免署名，[license](https://breakfastquay.com/technology/license.html)），走该路线需计入成本与署名要求。
9. **用户预期。** 「变声」二字会带来 Voicemod 式预期（音色克隆、大量预设）。若只做音高+共振峰，必须在文案里写清能力边界，避免被认为是半成品变声器。
10. **产品定位漂移。** 竞品分析明确记载「变声为主」是 Voicemod 的定位，而本产品以音效板与「装完即用」取胜。功能可以加，叙事不能偏。

### 7.2 未决问题（需产品或技术拍板）

1. 首发是否只做「预设」，还是开放半音/共振峰滑杆？
2. 是否要「关闭变声」的全局快捷方式（现场紧急还原）？
3. 预设是内置固定，还是允许用户 TOML 自定义（Hatsumi 路线）？
4. 是否购买 Rubber Band 商业授权换取更强共振峰，还是接受 Signalsmith 的共振峰质量？
5. 降噪（RNNoise）是否与变声同期做？建议分开交付，避免一次改动两个实时模块。
6. 「变声」在商业策略里是免费还是 Pro 卖点？现有商业文档已把变声写进付费能力，需要统一。
7. 校准麦克风在变声开启时的测量语义（旁路测量 or 测量变声后）。
8. 低配 Windows 机器上的 CPU 余量下限（例如 2 核笔记本能否稳定跑 ±7 半音 + 共振峰）。

## 8. 方案分级

### 8.1 最小可用（经典 DSP，预设制）

- **范围**：启用开关 + 3～5 个内置预设（例如女声、小孩、低沉、机器人、对讲机）；预设 = 音高半音 + 共振峰比例 + 可选机器人/带通效果。
- **技术**：Signalsmith Stretch（MIT）做音高与共振峰，**用 `Stretch::new()` 自选小块**（不得直接用默认预设）；机器人/带通用纯时域效果器（fundsp 或自写）；挂在采集侧重采样后。
- **不做**：用户自定义预设、热键切预设、降噪、神经网络、自听变声。
- **代价**：新增 C++ 构建；音频回调多约 20–50 ms 延迟（小块配置实测值）；GUI 混音区多一组控件；文档与许可声明更新。
- **验收**：
  - 回调内零分配（分配探测测试）；
  - 变声开启/关闭/切预设不产生咔哒声，待机与正式转发均生效；
  - 音效播放、试听、监听、自检、校准行为与现网一致（回归：[播放操作组合回归](播放操作组合回归.md)）；
  - 48 kHz 与 44.1 kHz 输入设备下预设听感一致；
  - 记录并公布变声开启时的算法延迟（用库的 latency 查询 + 环回实测），不超过约定预算；
  - macOS 真机环回听到变声人声；Windows CI 离线基准通过，Windows 真机另验；
  - `THIRD-PARTY-NOTICES.md` 含新依赖。

### 8.2 完整（可配置人声链路）

- **范围**：在最小可用之上增加：半音/共振峰滑杆、效果开关（噪声门、EQ、软削波、混响）、用户自定义预设（TOML）、热键与手机遥控切换预设、CLI 参数、变声旁路快捷键。
- **技术**：同上；降噪可选 `nnnoiseless`（BSD）；效果链参考 Hatsumi 的预设结构。
- **代价**：参数面与状态同步复杂度上升（命令队列 vs 原子参数）；热键语义扩展要与音效槽位热键并存；遥控页与文案增加；测试矩阵变大。
- **验收**：最小可用全部项，加上：
  - 参数实时调节无爆音、无预设切换残留；
  - 热键/遥控切换与 GUI 状态一致（异步代次/票据语义不被破坏）；
  - 配置往返、旧配置兼容、未知键保留；
  - CPU：目标低配机上开启全套效果仍满足回调时限（记录 P99）。

### 8.3 实验性（神经网络音色）

- **范围**：RVC 类音色迁移，用户加载模型文件得到「像某人」的音色。
- **技术**：独立进程或推理服务，与主混音进程以 PCM 管道相连；不要把 Torch/ORT 放进音频回调。可关注 Beatrice（宣称 CPU 单线程约 50 ms、带音高与共振峰）与 StreamVC 类流式模型（论文约 70.8 ms），它们证明「低延迟神经变声」存在，但都不等于本产品的可交付依赖。
- **代价**：端到端延迟参考值约 90–170 ms（RVC 官方数据）；模型体积与下载、GPU 驱动矩阵、崩溃隔离、许可证与肖像权/滥用风险；打包体积与签名复杂度显著上升。
- **验收**：只能作为「实验开关」发布，需单独写延迟与硬件要求说明；**不能**并入默认实时链路，也不能用它通过最小可用的延迟验收。
- **建议**：在经典 DSP 预设被用户验证有价值之前不要投入。

## 10. 数据流与边界小结

```
                    ┌──────────────── 控制侧（非实时）────────────────┐
                    │ 解码音效 → 重采样到输出率 → 槽位 PCM            │
                    │ 配置/预设/热键/遥控/IPC → 参数与命令队列          │
                    └───────────────────────┬────────────────────────┘
                                            │ 无锁命令 / 原子参数
┌─────────────────── 实时采集回调 ───────────┼────────────────────────┐
│ 真实麦克风 → 下混 → 漂移重采样 → 人声变换* → 环形缓冲               │
└───────────────────────────────────────────┼────────────────────────┘
┌─────────────────── 实时渲染回调 ───────────┼────────────────────────┐
│ 读环形 + 音效渲染 → 增益混音 → 前视限幅 → 电平表 → 虚拟设备输出       │
└───────────────────────────────────────────┴────────────────────────┘
* 人声变换：只作用于麦克风人声；旁路时零延迟。不进入音效、试听、监听。
监听流：仅音效（现状麦克风增益静音）——变声不改变该语义。
试听流：仅音效，独立工作线程。
自检：独立流与独立缓冲，不经过人声变换。
```

边界原则：**变声是人声转发路径上的一个可旁路处理块**，不新增播放状态来源，不绕过共用 `Playback` 门控，不改变单音效约束。
