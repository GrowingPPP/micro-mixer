### ⚠️ 一个必须记录在案的更正过程

本次标定中我先后给出过两个**错误结论**，都已纠正：

| 错误结论 | 真实原因 |
|---|---|
| "虚拟设备固定衰减 18 dB" | `ffmpeg` 的 `sine` 滤波器生成的是**峰值 0.125**，不是满幅 —— 我的参考电平假设错了 |
| "设备带 AGC/归一化，不能用于电平实验" | 我的**分段算法有 bug**（声道平均 + 阈值分段），造成假象 |

**最终结论：透明线性环回，增益极差 0.21 dB。**

> 这个过程本身就是一条重要的产品洞察：**这个品类的测量陷阱极多**（默认峰值不是满幅、声道平均会因延时产生梳状抵消、录音启动有 1.5 秒延迟、音乐动态会干扰分段）。
> **产品里的电平校准必须自己发测试信号并回读验证，绝不能信任任何第三方工具或系统的默认值。**

## 1. 测试前准备（5 分钟）

1. **退出豆包 App**。
   该虚拟设备属于豆包，测试中观察到过一次异常底噪（−24 dBFS），可能是它在写同一个设备。
2. 确认设备索引：`cd m0/tools && ./list_devices.sh`
3. 找一个**真人队友**，约好在 Discord / 游戏语音里配合 15 分钟。
4. **想好坐标方式**：测试期间你的麦克风被虚拟设备接管，**你说的话传不出去**。
   请用**文字聊天**告诉队友当前是第几档。

## 2. 工具清单

## 3. 实验 1：链路打通（15 分钟，验证 H3）

**目的**：确认 macOS 26 上"播放 → 虚拟麦克风 → 队友听到"这条链路本身能通。

| 步骤 | 操作 |
|---|---|
| 1 | 打开系统「音乐」App 或任意播放器，把**输出设备**设为 `豆包会议记录虚拟设备` |
| 2 | 打开 Discord（或目标游戏），把**输入设备（麦克风）**设为 `豆包会议记录虚拟设备` |
| 3 | 播放 `m0/work/m0_音乐_18dBFS.wav` |

## 4. 实验 2：降噪阈值测试 ★ 最关键（20 分钟，验证 H1）

**这是决定产品能不能成立的实验。**

```bash
cd m0/tools
./ab_test.sh 3 5 音乐 队友A_降噪开
```

脚本会依次送 5 档电平（−30 → −6 dBFS），每档 10 秒、间隔 5 秒，同时录下环回。

**要求队友先做一件事**：在语音软件里把 **噪声抑制 + 回声消除** 打开。

跑完一轮后，**让队友关掉噪声抑制和回声消除，再跑一轮**：

```bash
./ab_test.sh 3 5 音乐 队友A_降噪关
```

再用**语音素材**重复一轮（对照组——降噪应该保留人声）：

```bash
./ab_test.sh 3 5 语音 队友A_降噪开_语音
```

## 5. 实验 3：实时混音验证（15 分钟）

**目的**：验证"真实麦克风 + 音效同时送入虚拟麦克风"，且**你的说话声不会被音效压掉**。
实验 1、2 只测了纯音效；但产品是**混音**，这是两回事。

```bash
cd m0/tools
./mix_live.sh 1 5 ../work/m0_音乐_18dBFS.wav 0 -6
```

> 参数：`<真实麦克风索引> <虚拟设备输出索引> <音频文件> [麦克风增益dB] [音效增益dB]`
> 上面用的是内置麦克风（索引 1）。想用 USB 麦克风就改成 0。

音效会**循环播放**。请：

1. 对着麦克风正常说话 → 问队友**能否同时听到人声和音效**
2. 问队友：音效响起时，**你的说话声有没有被压低**（AGC 抽吸感）
3. 试着调整音效增益（`-12` → `-6` → `0`），找平衡点

| 项 | 结果 |
|---|---|
| 队友能同时听到人声和音效 | ☐ 是 ☐ 否 |
| 音效是否把说话声压低 | ☐ 无 ☐ 轻微 ☐ 明显 |
| 人声仍清晰时的最大音效增益 | ______ dB |
| 音效在人声之下是否仍清晰可辨 | ☐ 是 ☐ 否 |

> 💡 这个脚本其实就是**产品的核心功能**，只不过用 ffmpeg 而不是自研引擎实现的。
> 它跑通 = **架构可行性验证通过**。

## 6. 实验 4：全局热键（15 分钟，验证 H2）

**目的**：验证不切出游戏就能触发。**这是被严重低估的风险项。**

不写代码的替代验证：

| 方案 | 做法 |
|---|---|
| A（推荐） | 用 macOS「快捷指令」绑定一个**全局快捷键**，动作为播放某个测试音频 |
| B | 用 Karabiner-Elements 注册全局热键触发 `afplay` |
| C | 若你有 Soundpad 之类的现成工具，直接用 |

然后：

1. 启动目标游戏，**全屏模式**（不是窗口化）
2. 按热键
3. 观察是否触发

## 8. 汇总判定

| 假设 | 结论 | 依据 |
|---|---|---|
| **H1** 降噪不吃音频 | ☐ 成立 ☐ 部分成立 ☐ 不成立 | 实验 2 |
| **H2** 热键在游戏中可用 | ☐ 成立 ☐ 部分成立 ☐ 不成立 | 实验 4 |
| **H3** macOS 26 上链路可通 | ☐ 成立 ☐ 不成立 | 实验 1 |

### 决策规则

| 情况 | 决定 |
|---|---|
| H1 ✅ + H3 ✅ | **GO** → 进入 M1 |
| H1 ✅ + H2 ❌ | **GO，改设计** → 手机遥控提到 P0，热键降级为辅助 |
| H1 ⚠️（只有关降噪才行） | **GO，重定义产品** → "配置引导"从差异化升级为**核心功能** |
| H1 🔴 | **NO-GO** → 停下重新评估产品形态 |
| H3 ❌ | **改路线** → 自研 AudioServerPlugIn 提前 |
