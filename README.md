# 把音频播进麦克风 · 跨平台声卡

在游戏里按一个键，队友就听到你选的那段音频——同时你的真实说话声完全不受影响。

**当前状态**：macOS 端**图形界面已跑通** —— 多路音效 + 全局热键 + 实时混音 + 端到端自检。
命令行版与 GUI 共用同一套音频内核。

---

## 为什么需要它

游戏和语音软件**只从"录音端点"取声音**，系统里默认不存在"把播放流接回录音流"的通路。
所以想放音频给队友听，传统办法只能拿另一台设备外放、再把手机怼到麦克风旁边。

本产品造一个**虚拟麦克风**，把「真实麦克风 + 音效」实时混音后写进去——游戏以为那就是你的麦克风。

```
真实麦克风 ──► 下混单声道 ──► 漂移控制重采样 ──┐
                                             ├─► 环形缓冲 ──► 混音 ──► 限幅 ──► 虚拟麦克风
音效文件（预解码驻留内存）────────────────────┘
```

## 图形界面（推荐）

```bash
cd apps/mixer-gui
../../node_modules/.bin/tauri build          # 产出 .app
open ../../target/release/bundle/macos/音效板.app
```

界面：顶栏状态灯 + 运行时长；设置区（设备、音效来源、热键、增益，**运行中改增益立即生效**）；
音效卡片网格（点击或数字键 1-9 触发，播放中高亮并显示进度条）；底栏实时指标（水位/欠载/溢出/限幅）。

**每个音效可以单独调音量**（卡片下方的细滑杆，−40 ~ +12 dB）：
滑块变**橙色**表示在增益、变**红色**表示静音。调整立即生效，不用重播。

底栏有个**电平表** —— 这是产品里最重要的一个仪表：它直接回答"队友能不能听到我"。
绿色区间是 **−18 ~ −12 dBFS**，说话时指针落在这里最稳；太弱会变灰（语音软件的降噪可能把它当噪声滤掉），
接近上限会变黄。它量的是**限幅之后、真正送往虚拟麦克风**的信号。

**「监听」开关（默认开）** —— 触发的音效**同时放给你自己听**。

为什么这个开关很重要：音效只送往虚拟麦克风，**不进你的耳机**。所以在游戏里按 F1，
你自己什么都听不到，只能盲猜队友有没有收到 —— 很容易连按好几次。
打开监听后按一下就能听到，这是全屏游戏里唯一能确认"按下去了"的反馈。
不想听可以在设置区关掉。

**每张卡片左边有个 ▶ 试听按钮** —— 只放给你自己听（走系统默认输出），
队友听不到。没有它，想确认某个音效是什么就只能播给全队。

### 「停止」不会让你变哑巴

这是个**故意的设计**，也是这套东西最容易踩的坑：

游戏只能听一个麦克风。要用音效，就得把游戏的麦克风指向虚拟声卡 ——
而**指向虚拟声卡之后，"队友能不能听到你"就完全由本程序决定**了
（实测：引擎停止后虚拟声卡里是**精确的 0**，一片死寂）。

所以本程序里：

| 状态 | 你的声音 | 音效 | 游戏麦克风要改吗 |
|---|---|---|---|
| **音效已开启** | ✅ 队友听得到 | ✅ | 不用 |
| **待机**（点了「停止」） | ✅ **队友照样听得到** | ❌ | **不用** |
| **彻底释放** | ❌ 队友听不到 | ❌ | 要改回真实麦克风 |

也就是说：**「关闭音效」只是关掉音效，不会断掉麦克风转发**。
想放音效时点「开启音效」即可 —— 设备不重开，瞬间生效。

#### 界面上的两个"停止"按钮**完全不是一回事**

早期两个按钮都叫「停止」，用户实测后立刻问「这俩什么关系」—— 属于起名起坏了。现在改成：

| 按钮 | 位置 | 作用 | 麦克风 | 热键 |
|---|---|---|---|---|
| **关闭音效** / **开启音效** | 右上角 | 音效功能的**总开关**（关闭 = 进待机） | ✅ 继续转发 | 关闭后失效 |
| **停止播放**（空格） | 右下角 | 把**正在响**的音效掐掉（长音效不用等它放完） | ✅ 不受影响 | ✅ 不受影响 |

#### 点卡片 vs 点「试听」

| 操作 | 送到哪 | 队友 |
|---|---|---|
| **点卡片空白处**（或按热键） | 混进虚拟声卡 | ✅ 听得到 |
| **点卡片上的「试听」** | 你系统的默认输出 | ❌ 听不到（故意的） |

> 「试听」按钮原来是一个 `▶` 图标，用户实测时**误把它当成了播放键**（点了之后看到
> "试听中（队友听不到）"过来确认）。现在改成文字「试听」，并且正常播放后会提示
> 「已送进麦克风 —— 队友听得到」，两者形成明确对照。

> 只有点界面上的**「彻底释放音频设备」**（或退出程序）才会真的断开转发，
> 那时必须把游戏的麦克风改回真实麦克风，否则队友听不到你。

**音效库**（增删改查 / 标签 / 搜索）：

| 操作 | 怎么做 |
|---|---|
| **增** | 「文件夹…」整目录载入，或「添加文件…」多选挑单个 |
| **删** | 卡片右上角悬停出现 `×` —— 只从库里移除，**不删文件** |
| **改** | **双击名字**即可改名；卡片上的滑杆单独调音量 |
| **排序** | 卡片上 `←` `→` 前后移；或「按名称排序」 |
| **查** | 顶部搜索框，**音效名、标签、热键都能搜** |
| **标签** | **双击卡片上的标签区**即可编辑；搜索框右侧的标签条点一下只看这一类，再点取消 |

> 标签编辑认**中英文逗号、顿号、分号、竖线**（`音乐，常用、循环` 会拆成三个标签）——
> 用户打中文时很自然会用「，」，只认英文逗号会让人以为"输了没反应"。
> 输入框的占位提示会列出**库里已有的其他标签**，方便复用。
>
> ⚠️ 热键是**按位置**对应的，所以移动/排序时热键会跟着音效一起走 —— 不会出现
> "F1 换了个音效"的意外。
>
> 改音效库需要先点「停止」（避免运行中热键对应关系错乱）。

配置里以**并行数组**存放（`sound_files` / `sound_gains` / `sound_names` / `sound_tags`），
长度不一致会自动补齐；标签内部用 `|` 分隔（**不能用逗号** —— 配置的列表本身就是逗号分隔的，
标签里再放逗号会让整个数组错位，这条有单测锁着）。

**设置会被记住**（`~/.config/mixer/config.toml`），下次打开自动恢复；
CLI 和 GUI 共用同一份配置 —— 用哪个配都行。

**关闭窗口不会退出** —— 引擎继续跑，否则你一关窗队友就听不到你了。
菜单栏有个图标（均衡器样式），点它重新打开窗口，右键菜单可「全部停止 / 退出」。

`apps/mixer-gui/build-app.sh` 除了生成 `.app`，还会打一个 **DMG**：

```
target/release/bundle/dmg/音效板_0.1.0.dmg
```

**「首次打开请看这里.txt」**（说明 Gatekeeper 怎么过、虚拟声卡怎么装）。

> ⚠️ **DMG 必须在重新签名之后打**。交给 `tauri build` 顺手打包的话，
> 盘里装的会是**签名失效的那个版本** —— 用户装上去拿不到麦克风权限。
> 脚本里专门有一条校验：**挂载 DMG，确认里面那个 App 的签名仍然有效**，
> 以及 audio-input entitlement 和用途说明都在。缺一条就构建失败。

**没公证的后果（实测）**：

| 场景 | 结果 |
|---|---|
| 拷贝/U 盘/AirDrop 传过去（无隔离属性） | ✅ 直接能开 |
| 浏览器下载后双击（有隔离属性） | ⚠ **被 Gatekeeper 拦住**，需要「按住 Control 点它 → 打开」 |

这是**没有 Developer ID 证书 + 公证时的固有限制**，绕不过去。
要么按盘里的说明操作一次，要么申请证书（见下）。

## 命令行

```bash
# 1. 编译
cargo build --release

# 2. 看设备（找到虚拟声卡）
./target/release/mixer list

# 3. 端到端自检 —— 先确认整条链路是好的
./target/release/mixer selftest

# 4. 麦克风透传
./target/release/mixer passthrough --output "VB-Cable"

# 5. 配置一次，之后零参数启动
./target/release/mixer config set sound_dirs ~/Sounds
./target/release/mixer config set output_device "VB-Cable"
./target/release/mixer config set hotkeys F1,F2,F3
./target/release/mixer play                    # ← 之后只要这一条

# 6. 用手机遥控（热键被游戏吞掉时的兜底）
./target/release/mixer play --remote 8765
#    手机浏览器打开 http://<电脑IP>:8765 ，大按钮点一下就播
```

## 手机遥控（GUI 内置兜底）

设置区有个「手机遥控」开关（默认开）。启动后底栏会显示一个局域网地址，例如 `📱 192.168.1.12:8765`：
**手机浏览器打开它，就是一块大按钮音效面板**，点一下就播给队友听。

它**不依赖键盘、不依赖游戏、不依赖反作弊** —— 这是它存在的全部意义。
页面上还带一条**送往麦克风的电平条**，手机上也能看到队友听到的声音有多大。

**界面上有个「二维码」按钮**（常在，不随运行状态隐藏）—— 点开是遥控地址的二维码，
手机扫一下就能打开，不用手输 `10.220.179.90:8765` 这种地址。
（遥控是热键被游戏吞掉时的唯一退路，所以这一步越省事越好。）

> 遥控服务在点「停止」之后**仍在监听**（只是没有引擎可控制），所以地址一直有效，
> 二维码也一直可用。

> ⚠️ **两个实测踩到的坑**：
> 1. **地址不能靠"探测默认路由"** —— 开发机上默认路由常走 VPN，探到的是 `198.19.x.x`，
>    手机在局域网里根本连不上。现在枚举全部网卡并**按名字剔除 VPN/点对点/AWDL**，
>    打印的是真正的局域网地址（如 `10.220.179.90`）。
> 2. **macOS 防火墙默认会拦未签名程序的入站连接**。程序启动时会检测并打印放行命令：
>    ```
>    sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add "<程序路径>"
>    sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp "<程序路径>"
>    ```
遥控服务跨音频重启存活，手机上不用反复刷新。

## 热键被游戏吞掉怎么办

**这是本产品最大的未知风险**：部分全屏独占游戏会拦截系统级全局热键。

开游戏之前先验一下：

```bash
./target/release/mixer hotkey-test          # 按提示按键，程序会打印收到的时间
```

> ⚠️ **MacBook 键盘**：F1~F12 默认是媒体键（亮度/音量），必须**按住 fn** 才是真正的 F1。
> 也可以到「系统设置 → 键盘 → 键盘快捷键 → 功能键」把 F1/F2 用作标准功能键，
> 或直接改用 `--keys "Cmd+Shift+1,Cmd+Shift+2"` 这类组合键。

> ⚠️ **macOS 的硬性要求**（真机踩坑，有两层）：
>
> 1. 热键管理器**必须在主线程创建**
> 2. 主线程必须**真正在泵 Carbon 事件队列**
>
> 真机实测对照（用户实测 + 本机验证）：
>
> | 主线程在做什么 | 热键 |
> |---|---|
> | tao 的 NSApplication 事件循环（GUI） | ✅ **响应** |
> | `thread::sleep` 轮询 | ❌ 无反应 |
> | 裸 `CFRunLoopRunInMode` | ❌ 无反应 |
> | Carbon 原生 `RunApplicationEventLoop` | ⚠️ 能收到，但 `QuitApplicationEventLoop` **打不断它**（实测挂死） |
> | `hotkeys::run_app_event_loop()`（手泵 `ReceiveNextEvent`） | ✅ **响应**，可被打断 |
>
> 命令行程序的主线程**不能拿来做别的事**，必须让出来跑 `hotkeys::run_app_event_loop()`，
> 轮询逻辑放工作线程。GUI 由 tao 负责，只要保证管理器在主线程创建即可。
>
> 以上结论全部来自**真人按真键的实测**，不是推断。

先在桌面按一次（应当立刻响应），再切到**全屏游戏里**按一次：

| 结果 | 行动 |
|---|---|
| 游戏里也响应 | ✅ 直接用 |
| 只有窗口模式响应 | 把游戏改成"无边框窗口" |
| 全都不响应 | 用界面上/命令行的**手机遥控**，完全不依赖键盘 |

手机遥控是**刻意设计的兜底通路** —— 它绕开键盘、游戏和反作弊，只要手机和电脑在同一个局域网就能用。

然后把**游戏/语音软件的麦克风**选成同一个虚拟声卡，队友就能听到了。

### 可选参数

| 参数 | 说明 |
|---|---|
| `--loop` | 循环播放 |
| `--sfx-gain -6` | 音效增益（dB，可为负） |
| `--mic-gain 0` | 麦克风增益（dB） |
| `--buffer-ms 20` | 缓冲水位。卡顿就调大，延迟敏感就调小 |
| `--duration 20` | 跑固定秒数后自动退出（自动化测试用） |
| `--normalize` | 峰值归一化到 −3 dBFS |
| `--hotkeys F1,F2` | 逗号分隔的全局热键；省略则自动用 F1..Fn |

### 自检

`mixer selftest` 把一段已知的 440Hz 正弦送进虚拟设备，再从它的环回输入侧录回来，
核对**频率、时长、电平**三项。这是唯一能抓住"只在真实设备上出现"那类故障的手段 ——
开发中确实遇到过一个：引擎交给声卡的数据完全正确（440Hz），设备实际输出却是 872Hz。

### 诊断

```bash
# 把交给声卡的原始数据存下来，用于和录音对比
MIXER_DUMP=/tmp/out.f32 MIXER_DUMP_FRAMES=300000 ./target/release/mixer play --file x.wav
```

## 项目结构

```
crates/app-config/          配置（设备、音效目录、增益、热键）—— CLI 与 GUI 共用
  └── ~/.config/mixer/config.toml

crates/audio-core/          平台无关的音频核心
  ├── device.rs             设备抽象层 —— macOS / Windows 后端实现同一个 trait
  ├── engine.rs             混音引擎（实时安全：零分配、零加锁、零 IO）
  ├── resample.rs           线性重采样 + 时钟漂移控制器
  ├── limiter.rs            前视峰值限幅器（保证永不削波）
  └── decode.rs             多格式解码（mp3/m4a/flac/ogg/wav/aac/alac）

crates/backend-cpal/        cpal 后端 —— 一套代码同时覆盖 CoreAudio 与 WASAPI
crates/hotkeys/             全局热键（macOS Carbon / Windows RegisterHotKey，无需辅助功能权限）

apps/mixer-gui/             Tauri 图形界面
  ├── src/host.rs           音频宿主：专用线程持有 cpal 流（macOS 上流不是 Send）
  ├── src/smoke.rs          无窗口冒烟测试：跑通 GUI 调用的全部命令
  └── dist/                 纯静态前端（无打包器，靠 withGlobalTauri 调 Rust 命令）

apps/mixer-cli/             命令行入口（与 GUI 共用音频内核）
  ├── config.rs             配置读写（手写解析器，零依赖）
  ├── remote.rs             手机遥控：局域网 HTTP 触发
  └── selftest.rs           端到端自检：送已知信号，从环回量回来

m0/                         M0 可行性验证的素材与工具（已结项）
```

### 为什么这样分层

选**纯环回架构**（驱动只做环回，混音全在 App 内）带来一个关键红利：
**换成 Windows 只需要换 `backend-cpal` 与驱动，引擎、解码、限幅、UI 全部复用。**

## 健壮性

顺利路径之外，这些异常情况都有**自动化测试覆盖**（`--smoke` 会跑）：

| 情况 | 行为 |
|---|---|
| 未启动时点播放 / 停止 | 安全，不崩溃，也不假装成功 |
| 选了不存在的输出设备 | 明确报错：`找不到输出设备「xxx」。用 list 命令查看可用设备。` |
| 启动失败后重试 | 状态可恢复，能正常启动 |
| 音效列表为空 | 可启动，等价于纯麦克风透传 |
| 试听不存在的文件 / 损坏的文件 | **立刻报错**（不是静默失败） |
| 连续两次点启动 | 内部先停后起，不报"设备被占用" |
| 快速 start/stop ×30 | 无线程泄漏（内存零增长） |
| **重复启动 App** | 第二个实例自动退出，提示去菜单栏找已运行的窗口 |
| **音效文件夹里有坏文件** | **跳过坏的、加载好的**，并在界面上列出被跳过的文件 |
| 疯狂触发（连发 40 次） | 0 欠载 0 溢出 |
| 50 个音效 | 全部加载，约 1 秒 |

## 一键自检

界面右上角有个「**自检**」按钮（命令行是 `mixer selftest`）：把一段已知的 440 Hz
正弦送进虚拟设备，再**从它的环回输入侧录回来**，量频率 / 时长 / 电平。

```
✅ 自检通过 —— 豆包会议记录虚拟设备 整条链路正常
   设备  豆包会议记录虚拟设备
   ✅ 频率  438.3 Hz   期望 440.0 Hz
   ✅ 时长  2.01 s     期望 2.00 s
   ✅ 电平  -9.1 dBFS  期望 −40 ~ −3 dBFS
```

**为什么需要它**：开发中遇到过一个只在真实设备上出现、且非确定性的故障 ——
引擎交给声卡的数据完全正确（440 Hz），设备实际输出却成了 872 Hz。
单元测试抓不到这种问题，必须有一把"从设备里量回来"的尺子。

自检失败会**区分三种原因**，而不是笼统地说"没信号"：

| 现象 | 含义 | 怎么办 |
|---|---|---|
| 环回采到数据但**全是数字零** | 声卡输出侧没接到输入侧（环回开关没开） | 先重试；再查设备的 Loopback 开关 |
| 环回峰值**极弱**（< −60 dBFS） | 声卡音量被调到了很低或 0 | 音频 MIDI 设置里把音量拉回 1.0 |
| 有信号但**找不到测试音** | 通路是通的，测试音没到 | 多半是游戏/语音软件独占着该设备 |

### ⚠️ 一个只在「双击启动」时才出现的致命问题：麦克风权限

**症状**：从终端跑一切正常（自检 8/8 通过），但**双击 .app 启动后自检必定失败**，
报「环回通路：全零（−∞ dBFS）」—— 录音是一整片数字零，不报错、不崩溃。

**根因**（tccd 日志原文）：

```
Refusing authorization request for service kTCCServiceMicrophone
... without NSMicrophoneUsageDescription key
```

macOS **只有在 `Info.plist` 里声明了 `NSMicrophoneUsageDescription` 时才肯授予麦克风权限**。
缺了它，系统直接拒绝 —— 而这个 App 需要录麦克风才能把你的说话声混进去。

为什么之前一直没发现：从终端启动的进程，TCC 会把权限**归因给终端**（终端有麦克风权限），
所以命令行测试全部通过；只有双击启动时，权限才归因给 App 自己。

**两处修复**（缺一不可）：

1. `apps/mixer-gui/Info.plist` 里加 `NSMicrophoneUsageDescription`
2. **打包后重新 ad-hoc 签名** —— `tauri build` 合并 plist 后原签名会失效，而
   **TCC 权限绑定代码签名**，签名无效同样拿不到权限。

所以打包请走 `apps/mixer-gui/build-app.sh`（它会自动重签并校验），不要直接 `tauri build`。

程序启动时会**主动申请一次权限**，避免"点启动时才弹窗、流已经开着静音"的尴尬。

### 自检会**自动重试**

这个虚拟声卡已知会偶发异常（实测约 15 次开流出现 1 次音高翻倍），而"重开一次流"几乎总能恢复。
所以自检失败时**自己重开流重试，最多 3 次** —— 不用你手动再点一遍。

- 第 2 或第 3 次才成功 → 会明确告诉你"前几次是设备抽风，已自动恢复"
- 3 次都没过 → 告诉你"已自动重试 3 次，均未通过"，并给出**分三种原因**的排查方向

（命令行同理：`mixer selftest`）

进游戏之前点一下，就能把"音频链路"和"热键"两类问题分开。

## 验证方式（重要：必须验「双击启动」路径）

本项目踩过一个**只在双击启动时才出现**的致命问题（缺 `NSMicrophoneUsageDescription`
导致 macOS 拒绝麦克风权限，录音全为零）。而从终端直接跑二进制时，TCC 会把权限归因给
**终端**（终端本来就有权限），**所有命令行测试都会正常通过，完全掩盖这个 bug**。

所以验证必须包含：

```bash
m0/tools/app_verify.sh      # 用 open 启动（等同双击），检查 11 项
```

| 检查 | 判据 |
|---|---|
| Info.plist 有用途说明 | 缺了系统直接拒绝授权 |
| 代码签名有效 | **TCC 权限绑定签名**，签名坏了照样没权限 |
| 菜单栏 / 前端 / 热键 / 遥控 | 日志里出现对应就绪行 |
| **麦克风有真实信号** | `peak_db > -95`。**没权限时精确等于 −100（全零）—— 这是照妖镜** |
| 局域网地址可达 | 手机用的就是它 |
| **触发音效 → 环回录到 880 Hz** | 光看"引擎在跑"只是状态，**这条才是真的听到了声音** |

**关掉窗口之后引擎必须继续跑**（否则用户在游戏里就没声音了）。这条也验过：

```
关窗前 : running=true  设备=豆包会议记录虚拟设备  槽位=2
关窗后 : running=true  设备=豆包会议记录虚拟设备  槽位=2  可见=false
```

> 早期版本我只看"进程还在不在"就宣称"音频未中断"——**那是没验到位的**。
> 进程活着不等于引擎在跑。现在探针改成对比关窗**前后**的引擎状态。

### ⚠️ 签名方式会改变权限行为（这条我改错过两次，第三次才对）

同一个"录不到声音"，在不同签名方式下原因**完全不同**：

| 签名方式 | 麦克风用途说明 | 目录用途说明 | audio-input entitlement |
|---|---|---|---|
| **ad-hoc**（`codesign -s -`，不开强化运行时） | **必需** | 不需要 | 不需要 |
| **真证书 + 强化运行时**（`--options runtime`） | **必需** | **必需** | **必需** |

**ad-hoc 签名**：
- 缺 `NSMicrophoneUsageDescription` → tccd 直接拒绝（日志原文
  `Refusing authorization request ... without NSMicrophoneUsageDescription`），录音全零
- 读 `~/Downloads` 这类受保护目录**不需要**额外声明

**真证书 + 强化运行时**（`build-app.sh` 现在默认走这条）：
- 除了 Info.plist，**还必须给签名带上 `com.apple.security.device.audio-input`**
  （见 `apps/mixer-gui/entitlements.plist`）。缺了它**不报错、不弹窗**，
  只是麦克风录回来全是零（peak 精确等于 −100 dBFS）
- 读 `~/Downloads` **必须有** `NSDownloadsFolderUsageDescription`，
  否则文件读取**永久阻塞** —— 不报错、不超时，表现为「点了启动没反应」，
  日志停在参数那一行之后

`build-app.sh` 三条都会自动校验，缺一条直接构建失败。

#### 📌 这条结论我改错过两次，留作记录

1. **第一次**：加了三条目录用途说明后 App 起不来 → 结论"不要加权限声明"。
2. **第二次**：后来同样症状在**没有**那三条时也出现了 → 撤回上面的结论，
   归因于"待处理的麦克风授权弹窗"。
3. **第三次（现在）**：真正的原因是 —— **签名方式变了，权限要求也跟着变**。
   前两次都是在 ad-hoc 签名下观察的，所以"目录声明可有可无"；
   换成强化运行时之后它就变成硬性必需了。

> **教训：「去掉就好了」不等于「就是它导致的」，而「这次不是它」也不等于「永远不是它」。**
> 同一个现象在不同配置下可以有完全不同的成因 —— 结论必须**带上它成立的前提条件**，
> 否则换个签名方式就失效了。

## 稳定性

长时间挂着用是这个产品的常态（一局游戏几十分钟到几小时）。实测：

| 场景 | 结果 |
|---|---|
| **连续 10 分钟 + 周期性播放** | 内存稳定在 **20.3 MB**（第 120s→570s 仅波动 ±0.1 MB，无泄漏）；线程数稳定；**稳态欠载/溢出 = 0/0** |
| **渲染/采集比** | **1.0006** —— 两个独立时钟域的漂移被自适应重采样完全补偿 |
| **虚拟设备无任何客户端时**（先开 App、后开游戏） | 播放正常，0 溢出 —— 启动顺序不影响 |
| **反复「停止/启动」20 次** | 内存 44704 → 44752 KB（**总增长 48 KB**）—— 无泄漏。待机↔开启走快路不重开设备，所以比早期版本还干净 |
| **真实麦克风是否进了混音** | 麦 0dB 时输出 −44.7 dBFS（有信号）、−60dB 时 −100 dBFS（归零）|
| **单元测试并行重复跑 20 次** | 0 次崩溃（曾因 Carbon 事件队列非线程安全偶发 SIGSEGV） |

**设备占用顺序矩阵**（`m0/tools/order_test.sh`，三种顺序都验证过能出声）：

| 顺序 | 场景 | 结果 |
|---|---|---|
| A | App 先启动，游戏后启动 | ✅ 883 Hz 录到 |
| B | **游戏先启动（已在录音），才打开 App** —— 最常见的真实顺序 | ✅ 890 Hz 录到 |
| C | 虚拟设备完全没有客户端 | ✅ 885 Hz 录到 |

### ⚠️ 虚拟声卡偶发「音高翻倍」——已查明与本程序无关

实测约 **15 次开流出现 1 次**：送进去的是 880 Hz，设备输出的却是 1731 Hz。

**定位过程**（`MIXER_DUMP` 对照实验，同一次运行里同时抓两份数据）：

| 来源 | 主频 | 峰值 |
|---|---|---|
| **引擎交给声卡的原始 f32**（`MIXER_DUMP`） | **878.9 Hz** ✅ | 0.355 |
| **设备环回录回来的** | **1731.4 Hz** ❌ | 0.354 |

- 幅度一致、播放进度速率正常（0.9s→1.9s 正好 1 秒）、协商格式无警告
  → **引擎侧完全正确**
- 波形是干净的 1714 Hz 正弦（不是整流、不是噪声、不是两个源叠加）
- 设备标称采样率稳定 48000Hz/2ch，不漂移

**结论：问题在 cpal ↔ CoreAudio ↔ 第三方虚拟声卡这一层，不在本程序。**

**处理**：「停止 → 启动」重开一次音频流通常就正常。`mixer selftest` / 界面上的
「自检」按钮会检测到它，并直接告诉你这是设备层的问题（而不是让你去翻代码）。

### ⚠️ 一个踩过的坑：cpal 在 macOS 上不释放回调捕获的数据

隔离实测（`cargo run --release -p backend-cpal --example stream_leak`）：

| 闭包捕获 | 反复开流/关流的内存变化 |
|---|---|
| 什么都不捕获 | 19.5 → 20.6 MB（基本平稳） |
| 捕获 2.5 MB 样本 | 23.1 → 25.5 → 28.0 → 30.5 → 32.9 → **35.4 MB**（完美线性） |

**cpal drop 流时不会释放回调闭包捕获的数据。** 引擎持有全部音效样本，
直接塞进闭包的话，每次「停止/启动」就泄漏一整套音效
（实测 30 轮泄漏 106 MB）。

**对策**：引擎装进 `Arc<Mutex<Option<_>>>`，主线程也持一份；停止时把引擎**取走**，
样本立即释放，被 cpal 泄漏掉的只剩一个空壳。30 轮泄漏从 **106 MB 降到 7 MB**，
剩下的正好是 cpal 自身每轮开流的基础泄漏（与是否捕获数据无关）。

回归测试：`MIXER_CYCLES=30 ./音效板.app/Contents/MacOS/mixer-gui --smoke`，
按**曲线后段是否还在涨**判断（只看总量会把分配器缓存误判成泄漏）。
