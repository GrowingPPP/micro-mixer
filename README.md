# 把音频播进麦克风 · 跨平台声卡

在游戏里按一个键，队友就听到你选的那段音频——同时你的真实说话声完全不受影响。

**当前状态**

| 平台 | 状态 |
|---|---|
| **macOS** | ✅ **已跑通** —— 多路音效 + 全局热键 + 实时混音 + 端到端自检 |
| **Windows** | ⚠️ **代码就绪，但一次都没运行过** —— 见 [Windows 版](#windows-版代码就绪未实测) |

命令行版与 GUI 共用同一套音频内核。

---

## 为什么需要它

游戏和语音软件**只从"录音端点"取声音**，系统里默认不存在"把播放流接回录音流"的通路。
所以想放音频给队友听，传统办法只能拿另一台设备外放、再把手机怼到麦克风旁边。

本产品造一个**虚拟麦克风**，把「真实麦克风 + 音效」实时混音后写进去——游戏以为那就是你的麦克风。

```
真实麦克风 ──► 下混单声道 ──► 漂移控制重采样 ──┐
                                             ├─► 环形缓冲 ──► 混音 ──► 限幅 ──► 虚拟麦克风
音效文件（预解码驻留内存）────────────────────┘
```

## 构建与运行

### macOS

```bash
npm install                        # 只为了拿 Tauri CLI
./apps/mixer-gui/build-app.sh      # 编译 + 重新签名 + 打 DMG
open target/release/bundle/macos/音效板.app
```

> ⚠️ **必须走 `build-app.sh`，不要直接 `tauri build`。**
> `tauri build` 合并 Info.plist 后原有签名会失效，而 **TCC 权限绑定代码签名** ——
> 签名坏了拿不到麦克风权限，表现为"录音全是零、不报错"。
> 脚本会自动重新签名并校验（签名 / 用途说明 / entitlement / DMG 内一致性），
> 缺一条直接构建失败。权限要求随签名方式变化（这条我在开发中改错过两次），
> 完整排查过程见 [CHANGELOG](CHANGELOG.md#权限类都是不报错就是没声音)。

### Windows

**在 Windows 机器上**：

```powershell
npm install
powershell -ExecutionPolicy Bypass -File apps\mixer-gui\build-app-windows.ps1
```

脚本自带环境检查（Rust / Node / **WebView2 运行时**）、冒烟测试、NSIS 产物校验，
以及装完之后怎么配 VB-CABLE 的指引。跑完得到
`target\release\bundle\nsis\音效板_0.1.0_x64-setup.exe`。

**在 macOS 上不能构建 Windows 版**（实测过，不是推断）：

| 步骤 | 能否 | 卡在哪 |
|---|---|---|
| 编译出 `.exe` | ❌ | 缺 `link.exe`（MSVC 链接器，随 Visual Studio 发布） |
| 打 NSIS 安装包 | ❌ | Tauri 在非 Windows 宿主上**静默跳过**（实测退出码 0、什么都不产出） |
| 打 MSI | ❌ | WiX 是 .NET + Windows 专有 |

能做的只有**类型检查**（`tools/win-cross-check.sh`，用桩替掉 `llvm-rc`，
因为 `cargo check` 不链接）。详见 [Windows 版](#windows-版代码就绪未实测)。

### 图形界面（推荐）

界面：顶栏状态灯 + 运行时长；设置区（设备、音效来源、热键、增益，**运行中改增益立即生效**）；
音效卡片网格（点击或数字键 1-9 触发，播放中高亮并显示进度条）；底栏实时指标（水位/欠载/溢出/限幅）。

**每个音效可以单独调音量**（卡片下方的细滑杆，−40 ~ +12 dB）：
滑块变**橙色**表示在增益、变**红色**表示静音。调整立即生效，不用重播。

底栏有个**电平表** —— 这是产品里最重要的一个仪表：它直接回答"队友能不能听到我"。
绿色区间是 **−18 ~ −12 dBFS**，说话时指针落在这里最稳；太弱会变灰（语音软件的降噪可能把它当噪声滤掉），
接近上限会变黄。它量的是**限幅之后、真正送往虚拟麦克风**的信号。

**「监听」开关（默认开）** —— 触发的音效**同时放给你自己听**。

为什么这个开关很重要：音效只送往虚拟麦克风，**不进你的耳机**。所以在游戏里按 F1，
你自己什么都听不到，只能盲猜队友有没有收到 —— 很容易连按好几次。
打开监听后按一下就能听到，这是全屏游戏里唯一能确认"按下去了"的反馈。
不想听可以在设置区关掉。

**每张卡片左边有个 ▶ 试听按钮** —— 只放给你自己听（走系统默认输出），
队友听不到。没有它，想确认某个音效是什么就只能播给全队。

### 「停止」不会让你变哑巴

**这是个故意的设计，也是这套东西最容易踩的坑。** 游戏只能听一个麦克风；
要用音效就得把游戏的麦克风指向虚拟声卡 —— 而**指向之后"队友能不能听到你"
就完全由本程序决定了**（实测：引擎停止后虚拟声卡里是**精确的 0**，一片死寂）。

| 状态 | 你的声音 | 音效 | 游戏麦克风要改吗 |
|---|---|---|---|
| **音效已开启** | ✅ 队友听得到 | ✅ | 不用 |
| **待机**（点了「关闭音效」） | ✅ **队友照样听得到** | ❌ | **不用** |
| **彻底释放** | ❌ 队友听不到 | ❌ | 要改回真实麦克风 |

也就是说：**「关闭音效」只是关掉音效，不会断掉麦克风转发。** 想放音效时点「开启音效」即可 —— 设备不重开，瞬间生效。

#### 界面上的两个"停止"**完全不是一回事**

早期两个按钮都叫「停止」，用户实测后立刻问「这俩什么关系」—— 属于起名起坏了：

| 按钮 | 位置 | 作用 | 麦克风 | 热键 |
|---|---|---|---|---|
| **关闭音效** / **开启音效** | 右上角 | 音效功能的**总开关** | ✅ 继续转发 | 关闭后失效 |
| **停止播放**（空格） | 右下角 | 把**正在响**的音效掐掉 | ✅ 不受影响 | ✅ 不受影响 |

#### 点卡片 vs 点「试听」

| 操作 | 送到哪 | 队友 |
|---|---|---|
| **点卡片空白处**（或按热键） | 混进虚拟声卡 | ✅ 听得到 |
| **点卡片上的「试听」** | 你系统的默认输出 | ❌ 听不到（故意的） |

> 「试听」原来是个 `▶` 图标，用户实测时**误把它当成了播放键**。
> 现在改成文字，并且在正常播放后提示「已送进麦克风 —— 队友听得到」，形成明确对照。

> 只有点**「彻底释放音频设备」**（或退出程序）才会真的断开转发，
> 那时必须把游戏的麦克风改回真实麦克风。

**音效库**（增删改查 / 标签 / 搜索）：

| 操作 | 怎么做 |
|---|---|
| **增** | 「文件夹…」整目录载入，或「添加文件…」多选挑单个 |
| **删** | 卡片右上角悬停出现 `×` —— 只从库里移除，**不删文件** |
| **改** | **双击名字**即可改名；卡片上的滑杆单独调音量 |
| **排序** | 卡片上 `←` `→` 前后移；或「按名称排序」 |
| **查** | 顶部搜索框，**音效名、标签、热键都能搜** |
| **标签** | **双击卡片上的标签区**即可编辑；搜索框右侧的标签条点一下只看这一类，再点取消 |

> 标签编辑认**中英文逗号、顿号、分号、竖线**（`音乐，常用、循环` 会拆成三个标签）——
> 用户打中文时很自然会用「，」，只认英文逗号会让人以为"输了没反应"。
> 输入框的占位提示会列出**库里已有的其他标签**，方便复用。
>
> ⚠️ 热键是**按位置**对应的，所以移动/排序时热键会跟着音效一起走 —— 不会出现
> "F1 换了个音效"的意外。
>
> 改音效库需要先点「停止」（避免运行中热键对应关系错乱）。

配置里以**并行数组**存放（`sound_files` / `sound_gains` / `sound_names` / `sound_tags`），
长度不一致会自动补齐；标签内部用 `|` 分隔（**不能用逗号** —— 配置的列表本身就是逗号分隔的，
标签里再放逗号会让整个数组错位，这条有单测锁着）。

**设置会被记住**（`~/.config/mixer/config.toml`），下次打开自动恢复；
CLI 和 GUI 共用同一份配置 —— 用哪个配都行。

**关闭窗口不会退出** —— 引擎继续跑，否则你一关窗队友就听不到你了。
菜单栏有个图标（均衡器样式），点它重新打开窗口，右键菜单可「全部停止 / 退出」。

## 命令行

```bash
# 1. 编译
cargo build --release

# 2. 看设备（找到虚拟声卡）
./target/release/mixer list

# 3. 端到端自检 —— 先确认整条链路是好的
./target/release/mixer selftest

# 4. 麦克风透传
./target/release/mixer passthrough --output "VB-Cable"

# 5. 配置一次，之后零参数启动
./target/release/mixer config set sound_dirs ~/Sounds
./target/release/mixer config set output_device "VB-Cable"
./target/release/mixer config set hotkeys F1,F2,F3
./target/release/mixer play                    # ← 之后只要这一条

# 6. 用手机遥控（热键被游戏吞掉时的兜底）
./target/release/mixer play --remote 8765
#    手机浏览器打开 http://<电脑IP>:8765 ，大按钮点一下就播
```

## 手机遥控（GUI 内置兜底）

设置区有个「手机遥控」开关（默认开）。启动后底栏会显示一个局域网地址，例如 `📱 192.168.1.12:8765`：
**手机浏览器打开它，就是一块大按钮音效面板**，点一下就播给队友听。

它**不依赖键盘、不依赖游戏、不依赖反作弊** —— 这是它存在的全部意义。
页面上还带一条**送往麦克风的电平条**，手机上也能看到队友听到的声音有多大。

**界面上有个「二维码」按钮**（常在，不随运行状态隐藏）—— 点开是遥控地址的二维码，
手机扫一下就能打开，不用手输 `10.220.179.90:8765` 这种地址。
（遥控是热键被游戏吞掉时的唯一退路，所以这一步越省事越好。）

> 遥控服务在点「停止」之后**仍在监听**（只是没有引擎可控制），所以地址一直有效，
> 二维码也一直可用。

> ⚠️ 两个实测踩到的坑（地址探测不能走 VPN 默认路由、macOS 防火墙会拦未签名程序）
> 见 [CHANGELOG](CHANGELOG.md#修复过的问题)。

遥控服务跨音频重启存活，手机上不用反复刷新。

## 热键被游戏吞掉怎么办

**这是本产品最大的未知风险**：部分全屏独占游戏会拦截系统级全局热键。

开游戏之前先验一下：

```bash
./target/release/mixer hotkey-test          # 按提示按键，程序会打印收到的时间
```

> ⚠️ **MacBook 键盘**：F1~F12 默认是媒体键（亮度/音量），必须**按住 fn** 才是真正的 F1。
> 也可以到「系统设置 → 键盘 → 键盘快捷键 → 功能键」把 F1/F2 用作标准功能键，
> 或改用 `--keys "Cmd+Shift+1,Cmd+Shift+2"` 这类组合键。

> ⚠️ **macOS 有两条硬性要求**（真人按真键实测出来的，不是推断）：
> ① 热键管理器**必须在主线程创建**；② 主线程必须**真正在泵 Carbon 事件队列**。
> 光 `thread::sleep` 轮询或裸 `CFRunLoopRunInMode` **都收不到**事件。
> 命令行程序的主线程必须让出来跑 `hotkeys::run_app_event_loop()`。
> 完整的对照实验见 [CHANGELOG](CHANGELOG.md#热键类)。

先在桌面按一次（应当立刻响应），再切到**全屏游戏里**按一次：

| 结果 | 行动 |
|---|---|
| 游戏里也响应 | ✅ 直接用 |
| 只有窗口模式响应 | 把游戏改成"无边框窗口" |
| 全都不响应 | 用**手机遥控**，完全不依赖键盘 |

手机遥控是**刻意设计的兜底通路** —— 绕开键盘、游戏和反作弊，只要手机和电脑在同一局域网就能用。

然后把**游戏/语音软件的麦克风**选成同一个虚拟声卡，队友就能听到了。

### 可选参数

| 参数 | 说明 |
|---|---|
| `--loop` | 循环播放 |
| `--sfx-gain -6` | 音效增益（dB，可为负） |
| `--mic-gain 0` | 麦克风增益（dB） |
| `--buffer-ms 20` | 缓冲水位。卡顿就调大，延迟敏感就调小 |
| `--duration 20` | 跑固定秒数后自动退出（自动化测试用） |
| `--normalize` | 峰值归一化到 −3 dBFS |
| `--hotkeys F1,F2` | 逗号分隔的全局热键；省略则自动用 F1..Fn |

### 自检

先跑 `mixer doctor` 确认"该有的东西都在"，再跑 `mixer selftest` 验证"链路通不通" ——
两者的分工和失败排查见 [自检与诊断](#自检与诊断)。

## Windows 版（代码就绪，未实测）

### 交付物的准确说法

**目前没有 Windows 产物。** 存在的是源码 + 配置 + 一个从未运行过的构建脚本：

| | 状态 |
|---|---|
| Windows 源码改动 | ✅ 8/8 crate 交叉编译通过（**类型检查级别**） |
| NSIS 打包配置 | ✅ 通过 Tauri 官方 JSON schema 校验；图标是合法的 6 尺寸 ICO |
| `build-app-windows.ps1` | ✅ 存在，**从未运行过** |
| **Windows 可执行文件** | ❌ |
| **NSIS 安装包** | ❌ |
| **在 Windows 上运行过任何一次** | ❌ |

「交叉编译通过」的含义要说清楚：`cargo check` **只做类型检查，不生成二进制**。
`target/x86_64-pc-windows-msvc/debug/` 是空的。它证明的是"代码能编译"，
**不是**"有个 exe"。

### macOS 上为什么构建不了（实测，非推断）

用一个最小工程排除 Tauri 干扰后直接试：

```
error: linker `link.exe` not found
  = note: the msvc targets depend on the msvc linker
  = note: please ensure that Visual Studio 2017 or later ... were installed
```

| 步骤 | 能否 | 卡在哪 |
|---|---|---|
| 编译出 `.exe` | ❌ | `link.exe` 随 Visual Studio 发布，macOS 上**无法获得** |
| 打 NSIS 安装包 | ❌ | 实测 `tauri build --bundles nsis` 在 macOS 上**静默跳过**：编译完、退出码 0、无任何报错、不产出安装包 |
| 打 MSI | ❌ | WiX 是 .NET + Windows 专有 |

唯一理论上的口子是 mingw-w64（`brew` 可得）+ `--target x86_64-pc-windows-gnu`，
但 Tauri 的 Windows 分发不以 `-gnu` 为目标，而且**即使打出来也验证不了** ——
不能运行、不能测音频、不能按热键。那正是本项目反复在避免的"看起来做了"。

### 两边复用了多少

**音频引擎一行没改。** `crates/audio-core`（混音、重采样、限幅、解码）
为 Windows 编译时**零改动通过** —— 这是当初选「纯环回架构 + 后端隔离」的回报：
换平台只需要换 `backend-cpal` 和驱动，引擎、界面全部复用。

界面（`apps/mixer-gui/dist/`）是**纯静态、两端完全相同**，差异由后端按平台下发
（比如 Windows 推 VB-CABLE、给出「命名是反的」警告；macOS 推 BlackHole）。

### 移植过程中挖出来的三个真 bug

这三个都是**只在 Windows 上才会犯、在 macOS 上完全看不见**的：

1. **配置路径会跑到当前工作目录** —— `HOME` / `XDG_CONFIG_HOME` 在 Windows 上都不存在，
   旧实现一路回退到 `"."`。GUI 的 CWD 不可预测，用户看到的是"改完设置下次打开就没了"
2. **设备掉线检测会卡死** —— 非 macOS 分支用了 cpal 枚举设备，
   而紧邻的注释里明写着"**绝对不能**这么干（实测卡死）"。那个兜底分支从没被走到过
3. **`is_main_thread()` 是个返回 `true` 的桩** —— 会让热键建在 tokio 工作线程上，
   而那个线程不泵消息 → `WM_HOTKEY` 永不派发 → **热键完全失效且不报错**

第 3 个最典型：它不是"没写"，是"写了个看起来处理了的桩"，
**比没有更危险**。这也解释了为什么移植过程里持续在做同一件事：
**把看不见的分支变成看得见、能测的**（96 个单测里有 21 个跑在 macOS 上、验的是 Windows 分支）。

### 到 Windows 上怎么验

```powershell
npm install
powershell -ExecutionPolicy Bypass -File apps\mixer-gui\build-app-windows.ps1
```

装完之后**先跑这两条**，不用进游戏就能把环境问题和代码问题分开：

```
mixer doctor      # 环境体检：设备、虚拟声卡、配置、文件、热键
mixer selftest    # 链路自检：送信号进虚拟设备，从环回录回来验频率
```

`doctor` 查"该有的东西在不在"（秒出、不动音频设备），
`selftest` 验证"链路通不通"（要开音频、两三秒）。两条都是原生命令，两端通用。

### 已知会在首次实测时暴露问题的点

诚实列出来，免得把"编译通过"当成"能用"：

- `Hotkeys` 的 `unsafe impl Send` **只在代码层面论证过**，真实注册/注销没跑过
- Windows 上容器**故意泄漏**管理器（避免跨线程 `DestroyWindow`），泄漏量很小但没实测
- 托盘图标、关窗不退的行为在 Windows 上未确认
- VB-CABLE 到底是 16 位还是 32 位、采样率多少 —— **没见过真机**
- NSIS 安装包从未构建过
- 「切回真实麦克风」在 Windows 上**没有**（有意为之：那个功能是回滚 macOS 流程
  改过的系统默认设备，而 Windows 流程压根不改系统设置）

## 项目结构

```
crates/audio-core/     平台无关的音频核心（引擎 / 重采样 / 限幅 / 解码 / 设备抽象）
crates/backend-cpal/   cpal 后端 —— 一套代码同时覆盖 CoreAudio 与 WASAPI
crates/hotkeys/        全局热键（macOS Carbon / Windows RegisterHotKey）
crates/app-config/     配置读写（CLI 与 GUI 共用）
crates/remote/         手机遥控（局域网 HTTP + 二维码）
crates/selftest/       端到端自检

apps/mixer-gui/        Tauri 图形界面（src/host.rs 是音频宿主，dist/ 是纯静态前端）
apps/mixer-cli/        命令行入口

m0/                    M0 可行性验证的素材与工具（已结项）
tools/                 跨平台的开发工具（见「开发」一节）
```

> 配置、遥控、自检原先都塞在 `apps/mixer-cli/` 里，后来抽成了独立 crate ——
> 因为 GUI 也要用同一套，放在 CLI 下会形成反向依赖。
>
> 各目录的**职责边界与改动注意事项**见 [CONTRIBUTING](CONTRIBUTING.md#2-项目结构)。

### 为什么这样分层

选**纯环回架构**（驱动只做环回，混音全在 App 内）带来一个关键红利：
**换成 Windows 只需要换 `backend-cpal` 与驱动，引擎、解码、限幅、UI 全部复用。**

## 健壮性

顺利路径之外，这些异常情况都有**自动化测试覆盖**（`--smoke` 会跑）：

| 情况 | 行为 |
|---|---|
| 未启动时点播放 / 停止 | 安全，不崩溃，也不假装成功 |
| 选了不存在的输出设备 | 明确报错：`找不到输出设备「xxx」。用 list 命令查看可用设备。` |
| 启动失败后重试 | 状态可恢复，能正常启动 |
| 音效列表为空 | 可启动，等价于纯麦克风透传 |
| 试听不存在的文件 / 损坏的文件 | **立刻报错**（不是静默失败） |
| 连续两次点启动 | 内部先停后起，不报"设备被占用" |
| 快速 start/stop ×30 | 无线程泄漏（内存零增长） |
| **重复启动 App** | 第二个实例自动退出，提示去菜单栏找已运行的窗口 |
| **音效文件夹里有坏文件** | **跳过坏的、加载好的**，并在界面上列出被跳过的文件 |
| 疯狂触发（连发 40 次） | 0 欠载 0 溢出 |
| 50 个音效 | 全部加载，约 1 秒 |

## 自检与诊断

界面右上角有「**自检**」按钮（命令行是 `mixer selftest`）：把一段已知的 440 Hz 正弦
送进虚拟设备，再**从它的环回输入侧录回来**，量频率 / 时长 / 电平。

```
✅ 自检通过 —— 豆包会议记录虚拟设备 整条链路正常
   设备  豆包会议记录虚拟设备
   ✅ 频率  438.3 Hz   期望 440.0 Hz
   ✅ 时长  2.01 s     期望 2.00 s
   ✅ 电平  -9.1 dBFS  期望 −40 ~ −3 dBFS
```

**为什么需要它**：开发中遇到过一个只在真实设备上出现、且非确定性的故障 ——
引擎交给声卡的数据完全正确（440 Hz），设备实际输出却成了 872 Hz。
单元测试抓不到这种问题，必须有一把"从设备里量回来"的尺子。

自检失败会**区分三种原因**，而不是笼统地说"没信号"：

| 现象 | 含义 | 怎么办 |
|---|---|---|
| 环回采到数据但**全是数字零** | 声卡输出侧没接到输入侧（环回开关没开） | 先重试；再查设备的 Loopback 开关 |
| 环回峰值**极弱**（< −60 dBFS） | 声卡音量被调到了很低或 0 | 音频 MIDI 设置里把音量拉回 1.0 |
| 有信号但**找不到测试音** | 通路是通的，测试音没到 | 多半是游戏/语音软件独占着该设备 |

自检失败会**自己重开流重试，最多 3 次** —— 这个虚拟声卡已知偶发异常
（实测约 15 次开流出现 1 次音高翻倍），而重开一次几乎总能恢复。
第 2 或第 3 次才成功会明确告诉你"前几次是设备抽风，已自动恢复"。

进游戏之前点一下，就能把"音频链路"和"热键"两类问题分开。

### 验证必须包含「双击启动」路径

本项目踩过一个**只在双击启动时才出现**的致命问题（缺 `NSMicrophoneUsageDescription`
导致 macOS 拒绝麦克风权限，录音全为零）。而从终端直接跑二进制时，TCC 会把权限归因给
**终端**（终端本来就有权限），**所有命令行测试都会正常通过，完全掩盖这个 bug**。

```bash
m0/tools/app_verify.sh      # 用 open 启动（等同双击），检查 11 项
```

其中最关键的一条：**麦克风有真实信号**（`peak_db > -95`）——
**没权限时这个值精确等于 −100（全零），这是照妖镜**。

> ⚠️ **「权限要求」取决于签名方式**：ad-hoc 签名只要麦克风用途说明；
> 真证书 + 强化运行时则**三项都要**（用途说明 + 目录用途说明 + `audio-input` entitlement），
> 缺任一项都是"不报错、就是没声音"。这条结论我在开发中**改错过两次**，
> 前两次都是在 ad-hoc 下观察的。**完整的排查过程见
> [CHANGELOG](CHANGELOG.md#权限类都是不报错就是没声音)。**

## 稳定性

长时间挂着用是这个产品的常态（一局游戏几十分钟到几小时）。实测：

| 场景 | 结果 |
|---|---|
| **连续 10 分钟 + 周期性播放** | 内存稳定在 **20.3 MB**（第 120s→570s 仅波动 ±0.1 MB，无泄漏）；线程数稳定；**稳态欠载/溢出 = 0/0** |
| **渲染/采集比** | **1.0006** —— 两个独立时钟域的漂移被自适应重采样完全补偿 |
| **虚拟设备无任何客户端时**（先开 App、后开游戏） | 播放正常，0 溢出 —— 启动顺序不影响 |
| **反复「停止/启动」20 次** | 内存 44704 → 44752 KB（**总增长 48 KB**）—— 无泄漏。待机↔开启走快路不重开设备，所以比早期版本还干净 |
| **真实麦克风是否进了混音** | 麦 0dB 时输出 −44.7 dBFS（有信号）、−60dB 时 −100 dBFS（归零）|
| **单元测试并行重复跑 20 次** | 0 次崩溃（曾因 Carbon 事件队列非线程安全偶发 SIGSEGV） |

**设备占用顺序矩阵**（`m0/tools/order_test.sh`，三种顺序都验证过能出声）：

| 顺序 | 场景 | 结果 |
|---|---|---|
| A | App 先启动，游戏后启动 | ✅ 883 Hz 录到 |
| B | **游戏先启动（已在录音），才打开 App** —— 最常见的真实顺序 | ✅ 890 Hz 录到 |
| C | 虚拟设备完全没有客户端 | ✅ 885 Hz 录到 |

### 两个"外部原因"的坑（都不是本程序的问题）

**虚拟声卡偶发「音高翻倍」** —— 实测约 **15 次开流出现 1 次**：
送进去 880 Hz，设备输出 1731 Hz。同一次运行里对照两份数据：
引擎交给声卡的原始 f32 是 **878.9 Hz（正确）**，设备环回录回来是 **1731.4 Hz**。

**结论：问题在 cpal ↔ CoreAudio ↔ 第三方虚拟声卡这一层，不在本程序。**
「停止 → 启动」重开一次流通常就正常，自检会检测到并直接这么告诉你。

**cpal 在 macOS 上不释放回调捕获的数据** —— 两段对照实验隔离确认：
闭包什么都不捕获时内存平稳；捕获 2.5 MB 样本后每次开流/关流**完美线性增长**。
引擎持有全部音效样本，直接塞进闭包的话每次「停止/启动」就泄漏一整套音效
（实测 30 轮泄漏 **106 MB**）。对策是把引擎装进 `Arc<Mutex<Option<_>>>`、
停止时**取走**，30 轮降到 7 MB。

> 这两条的完整实验数据、以及另外几个内存问题的排查过程，见
> [CHANGELOG](CHANGELOG.md#修复过的问题)。

## 开发

**提交前跑这一条就够了：**

```bash
tools/check-all.sh          # 全部检查
tools/check-all.sh --fast   # 只跑静态 + 单元测试（约 8 秒，不碰音频设备）
```

当前结果：

```
静态：格式 ✅ · clippy 0 条 ✅ · 打包配置 schema ✅
逻辑：单元测试 96 个 ✅
端到端：打包 ✅ · 冒烟 37 项 ✅ · 音频自检 ✅ · 环境体检 ✅
        双击路径 11/11 ✅ · Windows 交叉编译 ✅
```

### tools/ 里都是什么

| 工具 | 作用 |
|---|---|
| `check-all.sh` | 一条命令跑完上面所有检查；`--fast` 跳过端到端 |
| `check-tauri-config.sh` | 用 **Tauri 官方 JSON schema** 校验打包配置 |
| `win-cross-check.sh` | Windows 交叉**类型检查**（用桩替掉 `llvm-rc`） |
| `gen-third-party-notices.py` | 生成 `THIRD-PARTY-NOTICES.md` |

其中前两个解决的是同一类问题：**错误只在"另一个平台/另一个时刻"才暴露**。

- 打包配置写错（键名拼错、枚举值写错）在 macOS 上**完全不会报错** ——
  那些字段只在真正构建对应平台时才被用到
- Windows 分支的代码在 macOS 上**完全不可见** —— 交叉编译是唯一能提前发现的手段
  （实测抓到过两次：我自己的 `Ordering` 未导入，以及一个会让热键完全失效的桩函数）

构建环境（国内网络）：

- Rust 工具链走 USTC 镜像安装
- `~/.cargo/config.toml` 已配置 crates.io 镜像（官方源在国内只有 ~35 KB/s）
